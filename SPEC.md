# momentum: one tool that keeps improving an agent system

Status: design. Phase 0 (the questions answered by hand, to set the baseline) is under way.

## Mandate

Reduce the work the owner spends supervising his agents. Improve, not only fix: how agents behave during a task, and the infrastructure they run on between tasks. Keep the owner's explicit instructions and constraints. Investigate with evidence, finish improvements within the authority already granted, measure whether each one helped, and bring the owner only the decisions that are his, with the evidence.

"I noticed something and wrote it down" is not an improvement. A change that shipped and measurably helped is.

## The questions it keeps asking

Each family is a standing question. A case is one answer in progress.

| Family | Standing question |
|---|---|
| Owner burden | What made the owner step in, correct an agent or lose patience, and what did the agent do just before? |
| Owner blind spots | What does the owner miss when he is tired or busy, and how can agents guard against it? |
| Manual work | What does the owner keep doing by hand, and what would do it for him? |
| Sessions | Which sessions stopped, stalled or wait on him, and which of those can move on without him? |
| Pressure | What load, memory, IO or money goes to waste, and what would cut it? |
| Capacity | What is trending to the edge (disk, quotas), what does every cleanup do by hand, and what did it miss? |
| Component health | Which installed component (memory, supervisors, guards, this tool) works poorly, measured? |
| Failures | Which tool or infrastructure failures recur, what is the root cause, and what fixes it at the source? |
| Outside | Which new system, model or result could replace a part of this setup, and does it win when tried here? |

## What it replaces

One tool, one case store, one loop, in place of separate scouts, boards, detectors and periodic review prompts: a findings scout with its curator and phone page, an incident detector with its investigator and escalation, the periodic tool-failure review, the "things I can pick up" scan, the session board and its watchdogs, and supervisors with nothing to supervise. During migration the existing phone page keeps working by reading this tool's cases.

It replaces them without adding a place to look. momentum has no app or dashboard of its own: its state shows inside surfaces the owner already looks at, the phone page among them, through its report (Report).

Two existing Go codebases are the starting point, not something to rewrite: a session board's per-harness scanners (live state of Claude Code, Codex, pi, opencode and Hermes sessions every 15 s, with no model in the loop) become the live session layer, and tacit's transcript readers serve history.

Session supervision is core, not a later extra. In Phase 0, most of the owner's manual work was asking sessions for status, answering approvals the agent had already recommended, running steps that need his identity, and nudging stopped sessions back to work.

## Boundaries

- **Knowledge stays in tacit.** The tool reads facts with tacit's search and fact interface and publishes a validated result with `tacit_add`, with its conditions and evidence. It keeps no second fact store, and a hypothesis is never written as a fact.
- **Personal content never enters this repository.** Cases, evidence and state live on the machine under the XDG directories (`~/.local/share/momentum`, `~/.config/momentum`). Never under `/tmp`.
- **Authority is inherited, not grown.** It follows the machine's shared agent rules and, for unattended runs, the scheduled-AI policy: external repositories and other people's issues are report-only, paid compute goes through the spend gate, and it never widens its own authority or changes its own evaluator to make a candidate pass.
- **Evidence keeps three lines visible:** the owner's own words versus generated text (subagents, compaction summaries, harness text, experiment prompts); a claimed completion versus an observed one; production work versus experiments, with experiments tagged so they never feed back as evidence of the owner's preferences.
  - On top of tacit's attribution rules, these do not count as owner text: the same text landing in two sessions within 2 s (a program sent it), wake-loop messages, agent briefs that open sessions, and momentum's own messages, which open with its marker (Supervision).
  - Prompts a tool pre-filled for the owner are kept but labeled: submitting them is still manual work.
  - Each owner turn also records its input kind (typed, queued, shell, slash command, answer to an agent question, accepted suggestion) and the system event just before it.

## Architecture

- **One native investigation per case.** The harness's main agent finds the mechanism, alternatives and fix from host-prepared evidence. It has a native brief and the owner's standing constraints. The host records its report. No family procedure is appended.
  - Prior art: Anthropic, ["When to fold subagents into your main agent loop"](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) (2026-10-22), and [`anthropics/single-agent-loop-kit`](https://github.com/anthropics/single-agent-loop-kit). Investigations use the harness's native agent and host bookkeeping.
- **Go.** tacit's shared readers supply transcript discovery, owner attribution and redaction. Host CLI commands ingest and inspect evidence and cases.
- **A CLI and systemd timers.** There is no daemon until a measured need appears.
- **No app or dashboard of its own.** Existing surfaces read `momentum report --json` (Report).
- **SQLite.** Events, cases and runs are kept locally. Reports and streams live beside the store.
- **Thin harness adapters.** Observation reads transcripts as the source of truth. Hooks add live signals but miss calls to absent tools.
- **A fixed sandbox launcher.** `internal/sandbox` uses bubblewrap in a transient systemd user service (Sandbox). The loop supplies the harness, relay and scrubbed read-only inputs. The launcher knows nothing about the harness, loop or store.

## Sandbox

`internal/sandbox` reuses bubblewrap, systemd and socat. It supplies one fixed argv, with no host shell. Anthropic's guidance puts the whole permission-free agent process in a container, VM or sandbox runtime, as a non-root user. Claude Code's shell sandbox alone does not cover the whole agent. OpenAI's guidance keeps keys behind a proxy and applies the diff in a separate job. The launcher is generic; the loop supplies the harness, relay and inputs.

```text
systemd-run --user --wait --pipe --collect --quiet --expand-environment=no --unit=momentum-run-ID
  -p MemoryMax=MEM -p MemorySwapMax=0 -p CPUQuota=CPU -p TasksMax=TASKS -p RuntimeMaxSec=SECS
  -p NoNewPrivileges=yes -p "RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK" --
bwrap --unshare-all --unshare-user --disable-userns --die-with-parent --new-session --clearenv
  --ro-bind /usr /usr
  --symlink usr/bin /bin --symlink usr/sbin /sbin --symlink usr/lib /lib --symlink usr/lib64 /lib64
  --ro-bind /etc/ld.so.cache /etc/ld.so.cache --ro-bind /etc/alternatives /etc/alternatives
  --ro-bind HOST/passwd /etc/passwd --ro-bind HOST/group /etc/group
  --proc /proc --dev /dev --tmpfs /tmp --dir /home/agent --dir /run
  (caller binds; optional --ro-bind SOCKET /run/relay.sock)
  --chdir DIR (--setenv NAME VALUE ...)
  /bin/sh -c 'socat TCP-LISTEN:8787,bind=127.0.0.1,fork,reuseaddr UNIX-CONNECT:/run/relay.sock & exec "$@"' sh PROGRAM ARGS...
```

With no relay the program runs directly. There is no socat or relay mount. `--expand-environment=no` preserves dollar expressions in program arguments and environment values for bubblewrap. The only network interface is private loopback. A relay run can reach its relay and anything the caller binds. It cannot reach host listeners, the host bus, an external address or DNS. The address-family filter also blocks AF_VSOCK, which a network namespace does not isolate. The relay owns authentication and request policy outside the sandbox.

**Layout.** The caller creates a private run directory (0700) with `work`, `out` and `ro`, and a private host-only sibling (0700) with inputs and the relay socket. Writable trees hold no sockets. An investigation's work tree is empty scratch. The host treats its files and output as untrusted data. It accepts only report text and a confined patch. Host programs and Git never run in writable run directories; the patch export is a separate sandbox job. Store inputs are scrubbed copies; SQLite copies use `VACUUM INTO` so they need no writable WAL. These are caller responsibilities, not launcher behavior.

A bind destination is exactly `/work`, `/out`, `/run/input`, or a path under `/ro/` or `/opt/`. Destinations are absolute and clean. None equals or contains another bind destination. No mount goes inside an untrusted mounted tree. A source is absolute, clean, exists, and is a regular file or directory, never a symbolic link, and none of its parents is one: callers pass paths they resolved (`filepath.EvalSymlinks`), so what the check saw is what bubblewrap mounts. A file with other hard links is bound as it is; the caller makes its sources. A directory is walked with `lstat`; a socket or an inspection error refuses the run. Internal symbolic links are not followed. The caller creates and keeps sources stable through launch; the launcher does not pin descriptors or protect against a host racing those checks. The relay is checked separately with `lstat`: it is a socket, owned by the caller, mode 0600 (ownership is checked in code; a test cannot make a socket of another user without privilege).

`Run` creates exclusive `passwd` and `group` files in `Host` and removes them when the client ends. They name `agent`, with the caller's UID and GID, home `/home/agent` and shell `/bin/sh`. The run preserves that identity, rather than becoming root. `/usr`, the two fixed `/etc` sources and the identity files are read-only. `/proc`, `/dev`, tmpfs `/tmp`, empty `/home/agent` and empty `/run` complete the fixed layout. The launcher mounts no momentum data of its own. Investigation callers bind their pinned evidence reader at `/opt/momentum/momentum-ro`; judges do not.

**Environment.** Bubblewrap clears the inherited environment. It sets only `HOME=/home/agent`, `PATH=/usr/bin:/bin`, `LANG=C.UTF-8` and `TMPDIR=/tmp`. The caller's map adds names or overrides those four. Names match `[A-Za-z_][A-Za-z0-9_]*`. NUL values are refused by name, without printing a value. Bubblewrap and the shell may add their own working-directory variables. Checks inspect names only. Stdin is empty. The caller supplies and bounds both output writers.

**Lifetime and limits.** Unit names match `momentum-run-[a-z0-9-]+`. Zero limit fields use the constants 4G, 400%, 512 tasks and 1800 seconds. Overrides become the unit's `MemoryMax`, `CPUQuota`, `TasksMax` and `RuntimeMaxSec`, alongside `MemorySwapMax=0` (swap is a separate limit in cgroup v2, and a run held to its memory does not spill into swap), `NoNewPrivileges` and `RestrictAddressFamilies`. The unit bounds the process tree and its tmpfs memory; the loop separately bounds turns, spend and output. `Run` starts and waits for the client. On cancellation it queues a stop of that exact service (`systemctl --user stop --no-block`) and, when the client has not ended in half a second, sends SIGKILL to every process of the unit (`systemctl --user kill`), repeating both every 100 ms until the client has ended: a SIGTERM that reaches bubblewrap while it is still setting up its namespaces can leave the program running (a 30-second sleep ran to its end after a stop 20 ms into the run), and a blocking stop would wait for that. Then it joins the client. The first failing write of an output writer ends the run the same way, and `Run` returns that error whatever the program's exit. Cleanup has a two-minute deadline, allowing systemd's default 90-second stop timeout. A broken manager is reported as a cleanup error; `RuntimeMaxSec` remains the last bound. `StopLeftover(ctx, prefix)` stops the loaded services whose names begin with a prefix of the caller's own (`momentum-run-loop-`, `momentum-run-eval-`; a test process uses a prefix of its own, so a test run never stops a live loop's or evaluation's units; a second evaluation fails at once on its lock, since its sweep would stop the first one's units) before it starts new runs, and no other caller's. `Command(ctx)` only builds the command; a caller using it directly owns identity files and unit cleanup. `Available()` makes a trivial real unit run; `Available(true)` also requires socat in the fixed system mount. Namespace tests skip with its reason when the environment cannot run the launcher, and a skip proves nothing about the boundary: with `MOMENTUM_REQUIRE_SANDBOX` set in the environment of `go test`, a skip is a failure.

**Exits.** `Run` returns `Result{Code, Failed}` and a separate error for validation, client startup, output copying, cancellation or cleanup. A program's nonzero exit is a result, not a Go error. Bubblewrap returns its program's exit code, or 128 plus the terminating signal. Bubblewrap setup failures exit 1 with a `bwrap:` diagnostic. On a nonzero exit, recognized stderr prefixes (`bwrap:`, `systemd-run:`, `Failed to `, `Job for `) mark an observed launcher failure. systemd-run propagates service failures too. Exit codes collide, silent manager or resource failures may have no distinct prefix, and a program can imitate one. `Failed` is a diagnostic hint. The caller checks whether it received the expected program result; exit status alone cannot prove which layer failed. Three cases read as an ordinary exit and a caller must not take them for a finished program: a unit stopped from outside (`systemctl --user stop`, a manager shutdown) makes `systemd-run --wait` return 0, so `Run` returns `Code 0`, no error and the output so far; a `RuntimeMaxSec` expiry and a `MemoryMax` kill both return 1 with no diagnostic. The loop is safe against all three because it takes a result only from the relay's authenticated report, never from an exit code. Unit names are unique among live runs: `Run` refuses a name the user manager already holds, since a second run cancelled at its start would stop the first.

**Checks.** A golden argv pins the fixed launch. Pure tests cover destinations, sources, environment names, unit names, socket modes and identity files. `testdata/inside-checks.sh` prints PASS or FAIL for identity, capabilities, files, environment names, processes, nested namespaces, AF_VSOCK and the relay. It reads `Seccomp: 2` and `NoNewPrivs: 1` inside. A live sleep test reads the unit's limits back from systemd and checks cancellation and collection. A Go HTTP relay on a Unix socket answers 503 and records the synthetic requests. Two host-only loopback listeners exercise host-port and outside-address refusal without external traffic.

Five test-only argv widenings must flip exactly these checks: shared networking (`interfaces`, `route-answers`, `other-loopback-port`, `outside-address`); the host home read-only (`home-entries`, `no-host-home`); inherited environment (`env-names`); shared PID namespace (`pid1`, `few-processes`); and no address-family filter (`vsock`). The PID widening skips if the kernel refuses its proc mount. The last test measures unfiltered AF_VSOCK availability and inherited seccomp first; it skips if the kernel cannot expose that socket. The package has no widening option.

**Ubuntu and fallback.** Ubuntu's bubblewrap 0.11.1-1ubuntu0.3 dropped the CVE-2026-87766 patch. The bug needs a mount destination inside an untrusted tree; the destination rule avoids that shape. The fallback is Anthropic's pinned `srt` 0.0.81 under the same unit, with an explicit file allow list and only the relay route. Rootless Podman with no network and the same socket plus socat is an independent alternative. Neither fallback is implemented here.

## Live session layer

The `sessions` packages are exported, so the session board imports them instead of keeping its own copy. They read processes, tmux panes, transcripts and the harnesses' own state, never a model, and one of them types into a session (Input):
- **Discovery:** Claude Code from the agent process under each tmux pane, Claude Code's per-process probe files and `claude agents --json`; Codex from its processes, the rollout files they hold open and its state database; pi, opencode and Hermes from their processes, session files and databases. Harness locations follow the harnesses' own variables (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_DATA_HOME`, `HERMES_HOME`, `PI_CODING_AGENT_DIR`). A `Lister` interface lets another tool's list stand in for native discovery.
- **Identity:** a session is keyed by its job, thread or session id, else by its process (pid and start time), never by a tmux pane id, which a restarted tmux server hands out again. Rows from another machine are dropped: their files are not here.
- **Phases:** needs_you, working, background, scheduled, idle, done. The rule, in order: a blocking ask gives needs_you (an async ask blocks only once its turn is over); an open turn gives working (a Claude Code turn is open while it waits on a model request, whatever opened it); tasks in flight give background; an error gives needs_you; a failed background job gives needs_you; a wakeup or loop gives scheduled; otherwise idle. Without a transcript, only the harness's own status counts, never a value a board wrote back.
- **Reviews:** only a model's review moves idle to needs_you or done, and only when it covered the same idle stretch and quotes the request word for word from the last message. The `verdict` package holds the prompt, the reply parser and that gate; the caller makes the model call.
- **Between runs:** each transcript tracker's place (Claude Code, Codex, pi) is a checkpoint in the store, one per transcript: the read position, what identifies the transcript (device and inode, its first 512 bytes, the 512 bytes before the position), and the state derived from what was read, with the activity log kept entry by entry. A run resumes from it and reads only what was appended. A transcript that shrank, was replaced, or was rewritten so that its first 512 bytes or the 512 bytes before the position changed is read again from the start. A checkpoint holds only what the transcript decided, never the clock or another file, so a resumed run derives what a full re-read derives. Only the build that wrote a checkpoint uses it: a run of another build reads the transcript in full and replaces it, so two builds used in turn both read in full. Checkpoints are derived: a schema step that reads again drops them, and one unused for 15 minutes is dropped. The database logs (opencode, Hermes) are read in full on every run, since both harnesses rewrite rows in place, which no cursor can tell. Hermes's log is the conversation as Hermes holds it, its active messages, so a turn it takes back and redoes with as many entries starts no new stretch. Sessions runs on one store take turns on a lock, from before the scan until the save; a run waits up to 10 seconds for the one before, then fails and names it. The checkpoint tables are a cache: when their columns are not this build's, they are made again, and only they are. When each session entered its phase is kept in the store's kept tables, which a schema change migrates and never drops (Store).
- **History:** each run compares the sessions it found with the stamps it saved and writes one event per change of stretch, with source `sessions`, actor harness, and the session's harness by its one name (Store): a session appeared, entered another phase, began a new stretch of the same phase after it moved between two runs, or vanished (unseen for 15 minutes by scans of its harness that worked: while a harness's scan keeps failing, its departures wait, and come dated at their last sighting). A session a source read only in part (a query of its own failed, or a Codex whose thread could not be looked up) changes nothing on that run. Its Meta holds the phases left and entered, the time in the phase left (up to the run that saw the change, and a lower bound up to the last run that saw the old phase), the session's name, and for needs_you the ask kind and text, entering and leaving. These events are observations: nothing can read them again, so `evidence rebuild` refuses them, and a schema change keeps them, as it keeps every event.
- **Attribution:** user-role text in the activity log is what the harness recorded in the user role, labelled with the harness's own origin when it gives one. It is not attribution to the owner; evidence about the owner comes from tacit's attribution.
- **Turns and reopenings:** a session says when user-role text last opened a turn (`UserAt`), by the harness's record, whoever typed it. A Claude Code session also says when its user last steered it without a prompt (`ControlAt`): a local command such as `/login`, whose echo strips to nothing, an interruption, or an answer to its question or plan (the result of `AskUserQuestion` or `ExitPlanMode`). An Escape that sends a queued prompt writes its interruption and the prompt a few milliseconds apart, in either order: an interruption within 2 seconds of a queued prompt written while the turn before it still ran, before anything of the prompt's turn (its request, a reply, a result, another input), ended the turn before the prompt, and the prompt's turn runs on, dated from the prompt. `Prompted`, which tells momentum's own Escape from its owner's, reads the same window. A permission approved between two scans leaves no record of its own. It also says when it was reopened after it ended mid-task, while nothing has happened in it since (`ResumedAt`): reopening it, Claude Code records the result of a call the end cut off, reports the background tasks that did not finish, and closes a turn the model owed with a synthetic "No response requested." without calling a model. It writes the same closing after an interruption, when the turn was not open; that is no reopening. The next assistant line or user text clears it. All three come from the transcript, so a checkpoint keeps them.
- **Requests and the queue:** a Claude Code session says when its turn sent the model request it still waits on (`RequestAt`): Claude Code writes an `api-request` record for a request its main thread sends, when its request recording is on (a feature of its own, which some requests skip), and the request waits while nothing of the conversation follows it. Without the records nothing here is set, and nothing acts on it. Any assistant record (a reply, an error), a user record the harness did not inject (a prompt, a tool's result, an interruption, a notification) or a system record other than a notice (the turn's end, a retry's error) answers it; a notice (a plugin reloaded), an attachment, a link or a queue operation does not, and a record dated before the request was part of it, written after it (Claude Code writes the request's own prompt so). It also counts the messages its user typed while the turn ran, which Claude Code holds in its queue (`Queued`, from its queue operations: an enqueue names what it adds, and one with no text is nearly always a scheduled run's prompt, another session's message or a notification, so it is not typed; a dequeue takes the oldest, a remove names what it takes, popAll takes everything back to the input line; a task's notification it queues is not typed). A reopening that closes a turn open on a request is a reopening, as for a typed prompt's turn. A slash command's prompt is no user text of its own (its echo is a command's, its body the harness's), so its request is what says its turn is open. Both come from the transcript, so a checkpoint keeps them.
- **Wakeups and loops:** a Claude Code session's wakeup (`ScheduleWakeup`) is pending from the result that set it until Claude Code records it firing (a `scheduled_task_fire` record of a loop's wakeup, by its kind or its words), or cancels it: another wakeup replaces it, the loop stops (`Loop stopped`) or reached its maximum age (`Wakeup not scheduled`), its user pressed Esc (the interruption record; an Esc at an idle prompt cancels it too, and leaves no record), or a restart came after its time (Claude Code's notice that the wakeup will not fire). A prompt does not take it over: it still fires after one, between turns. A restart in the foreground loses it; a background session's process arms it again, and the session layer does not know when that process started. While it is pending, a task's notification or a compaction is a sign that it may be lost (`WakeSign`): Claude Code is known to drop a wakeup for each, any notification while it is pending, after its time too, since a task that ran through its time sends its notification later. A job `CronCreate` scheduled runs on the expression its call named, in local time (recent versions write the schedule in words in the result, older ones the expression), recurring or once; the fire records name its runs by its task id, and a run of a task it does not know is neither the job's nor the wakeup's. Claude Code starts a recurring job's run late by up to half the gap to the next one and at most 30 minutes (a share a setting of its own can change), one every five minutes on time, 4 minutes 45 seconds after its last run or after it was made or restored, and a one-shot on time or a little early ([Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)); it never starts a run it missed while idle later (one a busy turn held starts when the turn ends). It reads a day field that holds every day as no restriction, refuses a step on a number (`5/15`) and a sign, and runs a minute of the wall clock once, so the hour a clock change repeats does not run again, even for a run delayed into it. A restart restores the jobs, session-only ones too (Claude Code resurrects them on a resume): a recurring one runs from its first run after the restart, a one-shot only if its time had not come. A recurring job expires 7 days after it was made. Claude Code writes its record of each run from version 2.1.291 on (the earliest the history shows writing one); with an older one, a run that started looks like one that did not, so the session lists no runs. The session lists its own runs (`Runs`), earliest first, a tie by key: its pending wakeup, and each job's runs since it last ran that never started, with its next (those of the last 2 hours, past which no rule acts on a run due while idle, 150 at most; none of a job a version that writes no record of its runs made). Each says the latest Claude Code starts it (the wakeup's time, or the run's and the most Claude Code delays it), what it is for (the wakeup's reason, else its prompt; the job's prompt), a key that names it on every scan, whether it is a job's or a one-shot's, and a wakeup's sign. The session also says when its last turn began (an input, or a scheduled run) and ended. It is scheduled while a wakeup is no more than `WakeGrace` (2 minutes) past its time, or a job is set; a run stays listed past that, until it starts.
- **Input:** package `act` is the one part of the layer that writes. It types a message into a session and submits it, as its owner would at the keyboard: a bracketed paste into the session's tmux pane and then Enter; kitty's remote control (send-text with bracketed paste, then the enter key) for a session in a bare kitty window; Codex's own queue (`codex queue --thread=ID --message=TEXT`) for a Codex thread with neither. One more path breaks a Claude Code turn that waits on a request with no reply (Interrupt, below).
  - It types only into a session it can show is waiting for input. Typed text would answer a dialog and Enter would pick its highlighted option; a draft would be sent with the message; a shell that stopped the agent would run it.
    - The terminal the keys go to runs the session's own process in its foreground: the pid and start ticks the scan found, under the pane's shell, its controlling terminal the pane's, not stopped, and its terminal's foreground process group; or for a kitty window, the one window the window id names (a number), with the process among its foreground processes.
    - No tmux mode owns the pane's keyboard, and the pane's input does not go to other panes (synchronized panes).
    - No dialog or menu is at the bottom of the screen: a permission prompt, a numbered choice under a selection cursor, a menu's key footer, a yes/no prompt, a resume or approval question. No turn is running there either: a message typed now would wait in its queue. A turn runs by the key that interrupts it at the bottom of the screen; on Claude Code's input box, by Claude Code's own rows around the box alone (Interrupt, below), whose running row stays while text on the input line hides the key.
    - The input line of the session's harness holds nothing typed: Claude Code's between its two rules (the top one may carry the session's name) or its older boxed prompt, Codex's `›` line. What a harness draws dim, its placeholder and its suggestion, is not typed. The cursor is a character drawn reversed: on a dim placeholder it sits on the placeholder's first letter, so a reversed character that dim text follows is the placeholder's. A screen with no input line it knows for the harness is a refusal, and so is every harness whose input line it does not know.
  - A refusal before the paste names its reason, and nothing was typed. After the paste it makes the same checks again and presses Enter only when the input line holds the message and nothing else, compared without whitespace, since a long message wraps; it reads the screen up to four times, a pause apart, for a terminal that draws the paste late or is caught mid-redraw. When a check fails then, or a command from the paste on fails, the error is `ErrUnstable`: the message may sit on the input line unsent, and when Enter itself failed, it may have gone through. A Codex queue command that ran and failed or timed out is `ErrUnstable` too: the thread may have taken the message.
  - The message is one line, its control characters dropped. One that would run as a command (it starts with `/`, `!`, `#`, `&` or `?`) is refused, and so is one that reads like the interface's own text (a menu row, a yes/no prompt, a running turn's line), which the check after the paste would take for a dialog. A Claude Code background session has no terminal of its own, and neither has a Hermes conversation on a messaging platform: no path reaches them.
  - **Interrupt** resumes a Claude Code turn whose model request never got its reply, the way its owner breaks one: it types the message into the input line while the turn runs, so Claude Code holds it in its queue, and presses Escape, which ends the turn and sends what the queue holds as the next prompt. It is the one write that is not a paste and Enter: Escape alone, with nothing queued, takes the turn back without a record and puts its prompt back on the input line, where a message cannot go; with a message queued, Claude Code records the interruption and the message as the next prompt. Tmux (`send-keys Escape`) and kitty (`send-key escape`) reach it; Codex's queue and every other harness do not.
    - Before the paste it checks the message and the terminal as above (the session's own process in the terminal's foreground, no tmux mode, no synchronized panes), no dialog or menu at the bottom of the screen, and an input line that holds nothing typed, read first: text on the line hides the interrupt key, and a draft is its owner at the pane. Then no message may wait in its queue, which Escape would send ahead of it, and the screen must show the turn running. The turn runs by Claude Code's own rows around its input box, never by the conversation above them. Its running row is the first row above the box that starts at the left edge, past blank rows and the indented rows Claude Code draws right under it (a tip, its task list, the first under `⎿`): a spinner glyph, what it does and an ellipsis, with how long it has run when the row has room (`✻ Fermenting… (31m 4s)`). With reduced motion Claude Code draws it with a still `●`, the glyph its conversation's messages start with too, so that row counts only with its time, and only after the paste. A retry notice takes that row's place (`Retrying in 4s · attempt 3/10`, `Waiting for API response · will retry in`, `No response from the API after`) and may wrap onto the rows under it. Below the box, the status line shows `esc to interrupt` while the input line is empty and the line has room. Before the paste it asks for what only a running turn shows: the key, the running row with its time, or a retry notice. A running row with no time is not enough then: the conversation draws a row like it for a thinking block. On a pane too narrow for the key and the time, a running turn reads as not running, so the rule takes it as taken back: no message, the needs note. Only Claude Code's input box between two rules is read: on its older boxed prompt, no turn runs. A message waits when the input line itself says, in what it draws dim, `queued message`, in any of Claude Code's wordings. A screen with no turn running (`ErrIdle`), or a message queued (`ErrQueued`), is a refusal and nothing was typed; `CheckInterrupt` makes these checks alone. Then it asks its caller once more (`still`: supervision reads the transcript for anything that answered the request since its scan, a later request among them, Claude Code's own retry, from which the wait starts again), and an answer there is a refusal too.
    - After the paste it presses Enter only when the input line holds the message and nothing else, with no dialog and the turn still running by its running row, with or without its time (Claude Code drops its `esc to interrupt` hint while text sits on the input line), reading the screen up to four times, a pause apart, and once `still` passes again. It presses Escape only once the input line is empty again and says that a message waits in the queue, with the turn running on screen, no dialog, and `still` passing again: a turn that ended meanwhile took the message as its prompt, and Escape would end the turn it opened. When a check fails from the paste on, or a command fails, the error is `ErrUnstable`: the message may sit on the input line, or in the queue. Whether the turn ended and the message went in, the transcript tells (Supervision, Sending); Interrupt does not wait for it.
  - Prior art: muster and its board's reply command (tmux `paste-buffer -p` then `send-keys Enter`, kitty `send-text --stdin`), and two public tools that type "continue" into agents. [unsnooze](https://github.com/saaranshM/unsnooze) proves the pane is the agent's and idle, and never presses a menu option blind. [tmux-codex-auto-continue](https://github.com/yeahdongcn/tmux-codex-auto-continue) fails closed unless the pane's foreground process is the agent, no tmux mode owns the keyboard, no menu shows, and the composer is empty or holds only the dim placeholder. A resume hook that sent keys into a dialog it did not read left its agents parked ([Roosevelt, "My resume hook came back alive and froze on the first question"](https://jonroosevelt.com/blog/my-resume-hook-came-back-alive-and-froze-on-the-first/), 2026-06). For Interrupt: Claude Code's documentation gives Escape as the way to stop a turn, and says it sends queued messages next ([Interactive mode](https://code.claude.com/docs/en/interactive-mode)); an open issue reports that in 2.1.0 Escape only moved queued prompts back to the input line ([anthropics/claude-code#16905](https://github.com/anthropics/claude-code/issues/16905)), which is why Interrupt presses Escape only once the screen says the message waits in the queue, and the transcript has the last word.

`momentum sessions` prints the live sessions and their phases from this layer.

## Supervision

`momentum supervise` keeps the owner's sessions moving when they stop without him, or wait on what never answers. It scans the sessions as `momentum sessions` does, runs deterministic rules over each one, types the message a live rule decides into the session (Input), and records every decision as an event of source `supervise`. No model takes part: each rule is a small function of what the session layer reads. The sessions timer runs it after each scan. A scan that came back short (a harness it could not read, an incomplete look at the machine) decides nothing, and a session a source read only in part is left for the next run.

- **The rules**, tried in order; the first that applies decides.
  - **transient:** the turn ended on a transient API error (the provider unavailable, a server error, the network). It sends a continue after a wait counted from the error that ended the turn, and after each try that ends on such an error again it waits longer: 10 minutes, then 4, 8 and 16. After four tries it opens a case and stops. A refusal, a prompt too long and an access error are not transient.
  - **access:** the turn ended on an expired login, a usage limit or an organization block. Trying again meets the same wall, so it resumes once access works again: at the reset time a limit states, plus a minute, or once a probe shows it. A stated reset before the error is a misreading, and so is a zone it does not know: then it waits for the probe. The probe is the first turn that worked on the Anthropic API in a session still blocked by an error of the same class when it worked (its last such error came after its last call that worked), since access stops a whole account and a session that never met the error, or met it once and has worked since, may run on another credential; for a login, also Claude Code rewriting its credentials after the error, which counts once the owner window after it has passed, since a login is the owner at the machine. Every session that stopped on it resumes. Three tries, one per sign, then a case. A rate limit Claude Code reports with no text of its own (an API error that says only "No response requested.") is a limit.
  - **cutoff:** Hermes stopped because the model's reply hit its output limit, and asks for `continue`. It sends that after 2 minutes; three tries, then a case.
  - **reopened:** the harness reopened the session after it ended mid-task (`ResumedAt`), or Hermes closed a turn a restart cut short, and nothing happened since: no call running, and a turn open only on the reopening's own notice, which no model answers until someone types. A resume prompt after 2 minutes, once.
  - **stalled:** a Claude Code turn waits on a model request that never got its reply: the last record of its conversation is the request (`RequestAt`), and no tool call is in flight. Background work does not answer the model: its notification waits in the queue behind the turn. After 30 minutes, counted from the request, or from the machine waking from a suspend that began before those 30 minutes ended (systemd's sleep target), it sends a resume message as the next prompt, on either screen: through Interrupt (Input) while the turn runs there, and the plain way, a paste and Enter, when the screen shows no turn running. That screen is a turn ended without a record while the transcript still waits on the request: an Escape with nothing queued leaves none, so its owner may have just taken the turn back. The first look that finds it, once per request, moves the rule's time to the owner window after it (a `wait` on record), and its stale hour with it; when that look finds the line he cleared, its wait ends with that hold. The message then goes in with the screen still showing no turn running, its line empty, and the transcript, read again from where the scan stopped, still showing the request unanswered. Only an owner who stays at the pane that long without typing goes unseen. Each message it sends, once the transcript shows it as the next prompt, is a decided note that says what it typed, which way, and into which session (Notes). A stall momentum cannot resume gets a needs note, its title what momentum could not do and why, and no case: at once when a look finds no path to it (no terminal it can type into), and at its stale hour when the last look before it was refused (a dialog, a draft that stayed, a screen neither check reads plainly: no turn running by Interrupt's check, a running row by the plain one, as on a pane too narrow for the row's time). It is written once the owner window has passed since he was last at the session. The note is decided from the record of the request's last look, not from one run's, so it stands while the rule holds and past its stale hour, and the last refusal's reason is its title. A look that goes through ends it, so it never stands beside a case or a message sent: each comes after one. A stall its owner held into its stale hour, with nothing refused at the last look, gets neither a message nor a note: he was there, and left it as it is. Claude Code's own retry is a new wait: the note about the request before it is done, and the retry gets its own. The Escape, like its owner's, also cancels a pending self-paced wakeup. Twice without an owner turn in between; then a case, once the request the second message's turn sent has waited as long without a reply (the message's own request is the stop the rule reads next, so a case at once would come before any reply could). A message its user queued waits for him, and a request of an earlier process is that process's. The message names nothing of the stall.
  - **overdue:** the turn is over, nothing is in flight, and one of the session's own runs came due long ago and never started: the earliest of its runs that no resync went in for and whose time is not past the stale hour, so a job that keeps missing its runs has each of them read. 10 minutes past the latest time Claude Code starts it, counted from the end of the last turn when it came due while that turn ran (a run waits for the turn), or from the machine waking from a suspend that began before the rule's time. A run due before the last turn began had its time then: the turn since does not start the wait again. An Esc at an idle prompt stops a self-paced loop and leaves no record, so a wakeup counts only with a sign that it was lost (its sign, or a suspend through its time), and even then its owner may have stopped the loop: its resync asks the session to go on only if the loop is still wanted, and to ask its user first when the conversation does not make that clear (Claude Code's own words for a wakeup a restart lost). A job's run needs no sign, since an Esc does not stop a job: its resync says the job keeps its schedule, and a second one that its runs are not starting, so to make it again if it is still wanted. A one-shot's says to do it now. Every resync quotes what the run was for and the date it was due. One resync per run, recorded once per run when the rule runs dry too; two for the same job or loop without an owner turn or a run of it that started in between (one whose turn worked does not start the count again), then a case at the time the third would have gone. Last words that ask the owner, and a stop of an earlier process, leave it alone.
  - **promise:** the turn ended, nothing is in flight or scheduled to wake it (no background task, wakeup or loop), and its last words promise to come back (report, check, wait for something) or announce a step it did not take. A resync prompt that quotes them, after 17 minutes; twice without an owner turn in between, then a case. Hermes runs background processes the session layer does not see, so this rule leaves Hermes alone.
  - A stop from before the session's process started belongs to an earlier process: only the reopened rule reads it. A rule whose own time came more than an hour ago does not act, held or not: nothing was watching then, or the owner left the stop as it is.
  - Tries count from the owner's last turn (the store's owner text) and from the rule's last message that worked, however long ago. A turn of his in the store that is one of momentum's messages, or opens with the marker within 3 minutes of one, is not his turn here: the store may have credited it to him. After a case, the rule sends nothing more to that session until his next turn.
  - The last words are read as the store keeps an agent's text, its first 160 and last 80 bytes without what a harness appended (Codex's memory citations), so the replay reads what the rule reads.
- **Never**, whatever the rule:
  - an automated run, a session on another machine (the layer drops those), or a Hermes conversation outside a terminal (any platform but its CLI and TUI, or an unknown one), which has no input line and whose reply would reach the owner's phone;
  - a session that asks its owner something: a blocking question, plan or permission, or last words that ask (the promise and reopened rules read them);
  - while the owner was at the session within the owner window, 15 minutes: the rule holds until it ends. He was there at his last turn by the store's owner text; at the harness's last user-role text (`UserAt`) unless it is one of momentum's own messages, word for word; at a local command, an interruption, or an answer to its question or plan (`ControlAt`), unless the interruption is momentum's own Escape (the interruption record the run that sent the message read in the transcript); when the sessions events show it leaving needs_you on a question, plan or permission (a permission approved between two scans leaves no record); whenever a check meets a draft on its input line or a tmux mode, and at the first check that finds the line empty after one (he cleared it); and when the session's process started (he opened it);
  - approve anything or answer a dialog: it types text only into an input line that holds nothing (Input);
  - wake the owner: nothing it does reaches his phone but the passive notes the report shows (Notes below). A case can also run a passive notice command from `sources.json`; there is none by default, and it is never a path that wakes him.
- **Messages** open with `[momentum]`, so the session, the owner and the evidence can tell them from his. The transcripts source stores a turn that is one of momentum's messages, word for word as momentum recorded typing it and compared before redaction masks anything, as harness text; it looks the texts up again for a turn it does not know, typed while it ran. A turn that opens with the marker and holds more (his words after a paste that stayed) is his. The transient message names nothing of the error, so no text that varies rides in it. One message per session per run, and none while the last one has not shown up.
- **Sending.** It checks the message and the terminal first (Input): a refusal is recorded once for the stop and try, the first time, and the next run checks again. A refusal that will not pass by itself opens a case, whichever check meets it: a message act will not type, no path into the session, or a harness whose input line act does not know. A stalled turn no path reaches gets its needs note instead (Notes). The stalled rule keeps its last look on record once per request, refused with its reason or gone through, for that note. Then the message is recorded as being sent before it is typed, so a run that dies after the Enter leaves a record that keeps the next one from typing it again, and the result replaces it: sent, or refused. A paste that may sit on the input line (`ErrUnstable`) opens a case. The stalled rule's message goes through Interrupt: its own checks come first (CheckInterrupt), their refusals handled as above (a draft or a tmux mode is its owner at the pane), then it is recorded as being sent with its Escape before anything is typed. When CheckInterrupt finds no turn running on the screen, the message goes the plain way: Check, then the transcript read from where the scan stopped must show the request still unanswered before the message is recorded as being sent, then Send types it. Either way the run then reads the transcript from where the scan stopped, for 10 seconds at most, for the message as the prompt of a turn; a turn that runs with nothing of it on the screen would hold a pasted message in its queue. On Interrupt's way it also notes the Escape's interruption, which Claude Code writes just before the prompt or as the next user record after it, within 2 seconds: a prompt that shows without it is read on for up to 2 seconds more, then taken as sent without one. A session whose place in its transcript the scan does not know gets nothing typed, a refusal before any check: nothing could tell whether the message went in. When the transcript does not show it, the message is in a state nobody can tell, `ErrUnstable`, and a case opens. The case's problem note stands while its turn is open and its last reply waits on no call (it may wait on a model request, or on a retry's backoff after an error): an open turn is not one that works again until a call runs.
- **Events**, source `supervise`, each keyed by the session, its stop and the rule, so the same decision on the next run is the same event; each message has a key of its own:
  - `act`: a message being sent, sent, or refused, with its try and path; or, for a rule that runs dry, the message it would have sent, tagged experiment `supervise-dry`;
  - `present`: the owner seen at the session's pane, one per stop, its time moved by each sighting: a draft, a tmux mode, the line he cleared;
  - `wait`, `hold`, `skip`: a decision not to act yet, or at all; also a session left for the next scan because a source read it only in part, a message still on its way, a scan that came back short, and the first look at a stalled turn's screen that showed no turn running, once per request (`wait`);
  - `outcome`: what came of a message on the next scans: delivered (a user-role entry of the session's since the send is the message), not delivered (not within 3 minutes, which opens a case), then worked (the turn made tool calls and stopped without an error), failed again (it stopped the way the rule reads), or stopped otherwise;
  - `case`: a rule used up its tries, a message did not land, or no message can. The case store (M2) takes them up.
  - They are momentum's own record: `evidence rebuild` refuses them, and a schema change keeps them.
- **Notes** for the report (Report):
  - a problem when a case opens (`store.SessionProblem`, id `supervise:KEY`, one per session, added once per case), done when the owner comes back to the session or it works again: a turn open (for Claude Code, one whose last reply waits on a call: an open turn may wait on a model request, or on a retry's backoff), or a stop since without an error;
  - a needs note (id `supervise-ask:KEY`, its title the question itself, or what momentum could not do) for a session that waits on what only its owner can answer: a question, plan or permission it asks him; a login or an organization block no sign of access has ended yet, or a usage limit that states no reset once it has outlasted the stale hour; an error no rule tries again, or one too old for its rule; a stalled turn momentum cannot resume (Supervision, the stalled rule), one per request, its title what momentum could not do and why; or a turn over and idle on words that ask him. It is written once the session has waited past the owner window, once per ask: a note he resolved while the session still waits on the same ask stays resolved, and one that stands takes the ask's latest title. It is done when the session moves on: the ask answered or another in its place, or the session ended. An automated run and a Hermes conversation on a messaging platform get none, and a session a run left alone keeps its notes as they are.
  - a decided note (id `supervise-resumed:KEY@MS`, the request's time in ms) for each stalled turn the rule resumed: the message it typed and which way (queued with Escape, or as the next prompt), into which session (its name, harness, pane and directory), and how to have the rule leave stalled turns alone. The report shows it for 12 hours.
- **Live and dry.** A rule sends only when it is live; the others record what they would have sent. The replay chose which: a rule is live when, over the owner's history, it acted unasked no more often than his own nudges went to a session that would have gone on by itself (a tool running, a task in flight, a wakeup due; none of them moves a turn that waits on a request nothing answered). `transient` and `access` ship live by the replay. `stalled` ships live by the owner's own call, over a replay that saw too few stalls to decide it; the replay's counts stay on the machine with the rest of the evidence. `cutoff`, `reopened`, `overdue` and `promise` run dry. `sources.json` can name the live rules instead, set the notice command, or turn supervision off:

```json
{"supervise": {"live": ["transient", "access", "stalled"], "notice": ["/path/to/notify"], "off": false}}
```

- **Replay.** `momentum supervise replay` runs the same rules over the store's history. Each input that opened a turn in an owner session gives one stop, rebuilt from the transcripts' events: the turn's end, the error, the last words, the background work, wakeups and loops registered, a reopening, the owner's last turn. For each stop it compares the time the first rule would act with what came next. Before the owner's labelled step (a nudge, a restart step) is covered, by so many minutes; the session going on by itself, the owner coming back with something else, or nothing coming at all are actions he did not ask for. `--labels` reads his steps, `--anchor` prints for each rule how long its stops sat before what came next (the data each wait is chosen from), and `--points` writes every stop. A notification the store cut is read whole from its transcript while the transcript is there.
  - The store keeps no request record, so a stop where the model owed its reply reads, from its transcript while the transcript is there, Claude Code's `api-request` records from the event before the one that left the reply owed (an input, or the result of a turn's last call; Claude Code may write the request before the record of the input it carries) to the next event, and none dated past the window, as the session layer reads them. A turn that waited at least a minute on its model where no input ended the wait is a stop of its own, and only the stalled rule reads it: the reply came (the session went on by itself), or the session was reopened, which closed the turn (its owner's restart).
  - It measures each stop's first try only, and builds its facts from the transcripts' events rather than the live layer: a stop's time is its last event, not the phase stamp; the owner window counts his owner text, his local commands and shell escapes, and his interruptions, but not an ask he answered or a refusal that showed him at the pane; a wakeup that never fired keeps its stop scheduled, and a cron never expires for the phase; the replay follows wakeups and jobs as the session layer does, reading a scheduled run's record (`scheduled_task_fire`, before its prompt) and a call's input from the transcript while it is there, else the run's prompt and the store's summary; it sees a restart by its reopening records or by a new Claude Code version in the records, and takes each for one in the foreground, and a suspend not at all, so a wait counts from its request and no suspend is a sign. A stop whose rule's time came more than the stale hour before it is past, as a live run would find it, and the overdue rule acts once per wakeup or run. The replay reads no screen, so it puts a stalled turn's message at the rule's time, where a live run on a screen that shows no turn running sends it the owner window later. A live run can differ from the replay in those ways.
- **Ingest.** The owner's turns, the re-credit of momentum's messages and the access probe come from the store's transcript events, so `momentum evidence ingest` must run on its timer, every few minutes: a sign the store learns more than an hour late is past.
- **Thresholds** are chosen with the replay: each wait sits past what the history shows the owner, and the sessions by themselves, doing at stops of its kind, and the transient waits double after the first, past what a failed try costs (Claude Code's own retries), until together they span the longest outage in the history. The stalled wait sits past the longest wait for a reply in the history (a subagent at the most effort, thinking near its whole output limit), past that limit streamed at the slowest thinking rate seen, and below every stall the owner broke by hand. A suspend makes a reply look late, so the wait counts from the wake. The values: the owner window 15 minutes; transient 10, 4, 8 and 16 minutes; a reset's grace 1 minute; cutoff and reopened 2 minutes; stalled 30 minutes; overdue 10 minutes; promise 17 minutes; a stop past after an hour. The overdue slack sits past the latest a wakeup or a job's run that did fire came in the history, counted as the rule counts it (from the later of its latest time and the end of the turn it came due in), the jobs read by the expressions their calls named.
- **Prior art.** [unsnooze](https://github.com/saaranshM/unsnooze) waits for a usage limit's reset and resumes every session it stopped, verifying each wake and rescheduling up to five times; momentum does the same for limits and adds the login and organization probes. [tmux-codex-auto-continue](https://github.com/yeahdongcn/tmux-codex-auto-continue) types `Continue` into Codex after its transient errors, at once; momentum waits first, since the store shows sessions with their own wakes resuming by themselves. The [OpenHands stuck detector](https://docs.openhands.dev/sdk/guides/agent-stuck-detector) nudges an agent caught in a loop with a message that names what repeats; momentum's resync quotes the promise the turn ended on. Claude Code retries an API error itself before the turn ends on it, which is why a failed try costs minutes.
  - For stalled requests: Claude Code runs its own streaming watchdogs, and documents that a request with no answer on Amazon Bedrock ends after 5 to 6 minutes ([Streaming idle watchdogs](https://code.claude.com/docs/en/network-config.md#streaming-idle-watchdogs)), and a retry, which the transcript records as a new request; its open issue [#33949](https://github.com/anthropics/claude-code/issues/33949) finds streams that hang with no timeout when a connection dies silently, and the history shows requests no watchdog ended. [agent-yes #89](https://github.com/snomiao/agent-yes/issues/89) proposes calling a busy frame with no output for a while wedged, and recovering with Escape, then a kill and `--continue`; momentum reads the transcript instead of the terminal's output, never kills, and opens a case when its Escape does not show. [pi #8331](https://github.com/earendil-works/pi/issues/8331) saw sessions frozen 25 to 109 minutes while every turn that finished took under 8, and proposes a 180-second inactivity timer inside the agent; [opencode #40010](https://github.com/anomalyco/opencode/pull/40010) (closed unmerged) an idle watchdog that learns between 15 and 30 minutes from the streams that worked. A watchdog inside the agent sees the bytes; momentum sees only records, and a model that thinks writes nothing until its first block, so its wait is longer.
  - For wakeups that never came: Claude Code fires a scheduled run between turns, with no catch-up for a missed one ([Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)), and its issues report wakeups that never fire: dropped when a background agent's notification re-enters the session or across a sleep ([#74569](https://github.com/anthropics/claude-code/issues/74569), open), silent across a compaction with the loop's cron and the notifications ([#89248](https://github.com/anthropics/claude-code/issues/89248)), one-shots that vanish before their time, worked around with a keeper cron that re-arms them ([#80679](https://github.com/anthropics/claude-code/issues/80679)); those triggers are the signs the rule asks of a self-paced wakeup. The documentation says an Esc stops a self-paced loop while it waits, and that an iteration that neither reschedules nor stops gets one fallback wakeup about 20 minutes later, which leaves no record either. Heartbeat monitors for cron and systemd timers (dead man's switches) alert when a run has not reported within its schedule and a grace period; momentum reads the schedule and the runs from the transcript, waits out the run's documented delay and a slack, and asks the session to do what the run was for instead of paging anyone.

## Session history

`momentum evidence ingest` reads every harness's retained session history under each home that `sources.json` lists (`"transcripts": {"homes": ["~"]}`). tacit's reader (`pkg/evidence`) reads Claude Code with its subagents, Codex with its compressed rollouts, pi with its tasks, and the Hermes store. Native adapters in `internal/source` read OpenCode, Grok and Kimi. They use the same event writer, redaction, actor rules and kept columns. tacit's attribution primitives split generated frames from owner text; native provenance decides whether a user-role item can be the owner's. tacit cuts the owner's pastes by the prompt history of `$HOME`, also in another home's sessions.

The homes discover OpenCode's `opencode/opencode.db` below `XDG_DATA_HOME` (else `~/.local/share`), Grok's `sessions` below `GROK_HOME` (else `~/.grok`), and Kimi's `sessions` below `KIMI_CODE_HOME` (else `~/.kimi-code`). Additional native locations use the same configuration: `"transcripts": {"sources": [{"harness": "opencode", "db": "~/history/opencode.db"}, {"harness": "kimi", "glob": "~/history/*/agents/*/wire.jsonl"}]}`. Homes and additional sources can be used together or separately. Source harnesses are opencode, grok and kimi. OpenCode requires `db`; Grok and Kimi require `glob`. An unknown harness, a missing location or the wrong location field is refused at configuration load, with the known source harnesses named. This does not edit a machine's configuration.

Coverage below describes recorded evidence, not every failure that could happen. Since names the reader's support, not a machine's first use. Every reader backfills retained history at its first ingest; it cannot reconstruct a deleted transcript.

| OpenCode | legacy session/message/part and V2 session_v2/session_message SQLite | Native adapter; retained rows | Covered for tool states, mutable results and setup diagnostics | Not for role-only main-thread input: the stored formats do not prove who submitted it. Synthetic and child input is generated | Partly: legacy/V2 live phases; owner nudge replay requires attributed turns; no delivery adapter |
| Grok | sessions' ACP updates.jsonl; summary.json supplies provenance | Native adapter; retained history | Covered for failed tool status and explicit output diagnostics | Partly: interactive session kind; headless/subagent input is generated; missing provenance is unknown | Partly: attributed transcript nudges; no live scanner or delivery adapter |
| Kimi | sessions' agents/main and child agents' wire.jsonl | Native adapter; retained current wire dialect | Covered for tool result flags, explicit exits/refusals and setup diagnostics | Covered for main user-origin prompts; tasks, system triggers and child prompts are generated | Partly: attributed transcript nudges; no live scanner or delivery adapter |

OpenCode's old storage tree without session/message/part transcripts is not a history source. Grok project metadata is not a transcript. A Kimi context file from another dialect is not an empty substitute for a wire reader.

- **Native formats.** OpenCode prefers V2 for a session with V2 messages, so its migrated legacy copy is not counted too. A changed session is read again by stable message id: tools update their state in place. A message or part with invalid JSON is skipped and counted, and the rest of its session is stored. A shell result's failure is its non-zero `metadata.exit` or its `error` status, never its output text. The reference names the database by its path, so a database moved to another path is read again under new keys. Its fingerprint uses row counts and sums of update times, plus session metadata. It does not read message or part bodies. An edit that preserves all of these is not detected. Grok reads ACP user/agent text, tool calls and terminal updates, turn ends and compaction summaries; a tool's metadata or `rawOutput.name` names it, never a title that may be a command. Its failed status marks any tool; a Bash envelope also supplies its command's exit. Search exit 1 with no matches is not a failure. Kimi reads turn.prompt/turn.steer and context.append_loop_event text/call/result records, turn ends and compactions. Its appended UI messages and context copies duplicate those records and are not counted again. Thought content is not agent text.
  - Grok uses seconds; Kimi and OpenCode use milliseconds. Native JSONL cursors keep their session, provenance, prior turn marker and outstanding call names. A terminal result removes its call from that state. A complete last record without a newline is read; a partial one stays before the cursor. Blank, malformed complete and non-object records are counted as skipped, recorded by their offsets without their text, and do not stop the file. Native record keys include the harness, session and agent, since many files share the name wire.jsonl or updates.jsonl.
  - OpenCode's role-only user input is kept with unknown attribution. Its global prompt history has no session or time, so matching text there cannot prove who submitted a particular turn. No owner event is invented. The live activity log's user role remains a role, as elsewhere in the sessions layer.
  - Native format references: xAI's [session persistence](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/README.md), Moonshot's [data locations](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/configuration/data-locations.md), and OpenCode's [API events](https://dev.opencode.ai/v2/docs/api) and [compaction storage](https://opencode.ai/v2/docs/compaction). The adapters follow the retained database/wire schemas, not a model API's role alone.

- **One event per item.** The actor follows the kind: the owner's text is the owner's; an agent's text and its tool calls are the agent's; a tool's result is the tool's; harness text and compactions are the harness's. A call the owner made himself (a command he ran from pi's prompt) is his, and an item tacit credits to no one is `unknown`.
  - Each event carries the session, the subagent, the harness, the model and the working directory. A Codex subagent's thread, a pi task and a Hermes delegation are a subagent inside their parent's session, as Claude Code's subagents are; a thread's own subagents are in the session of its id, and a session's listing walks them at any depth.
  - Its kind is tacit's (`owner_text`, `agent_text`, `harness_text`, `tool_call`, `tool_result`, `compaction`), and its tool is the tool's name.
  - Its meta holds the tool call's id, the error flag, how the owner's turn was put in (`input_kind`), the harness's record before it (`prior`), tacit's reason (`why`, when it says more than the kind) and the parent session.
  - Its reference is `path@offset#index`, the item's place in the transcript (a Hermes row's id). A native OpenCode reference names the database and message id before that place. A tacit file key is its own name with that place, so it holds when a harness moves or compresses the file. Native JSONL keys include the session and agent, since their files share names.
- **What is stored.** Every item except Codex's "[Recorded tool history]" messages, which replay calls and results that are already events. tacit's reader passes over a line it cannot parse, so this source counts no unparsed records. Tool calls and results are what a failure is reconstructed from; the owner's words are what the families start from.
  - A summary is clipped, in bytes. An owner's turn keeps 2,000: his words are what the families quote, and a typed turn is seldom longer. An error's output keeps 1,000, because it holds the failure. Other results, calls, harness text and compactions keep 240. An agent's text keeps its first 160 and last 80: what it set out to do, and what it asks or claims.
  - The full text stays in the transcript, at the reference.
- **Redaction.** Events hold only text that tacit's redaction masked (scrump).
  - Each text is cut with a 512-byte spare before it is masked, so a secret across the cut is whole when scrump sees it, and cut to its length after. An agent text's start and end are two texts. A result's native flag or status and the permitted shell wrapper signals are read before the cut. A failure keeps the error's 1,000 bytes even when its exit code was after the normal 240-byte cut.
  - A worker gathers up to 4 MiB of texts for one scrump call (a call costs a process start). Each text is masked as it would be alone.
  - scrump scans its input as one stream, so a hit that starts in one text could run into the next: a quoted value a cut left open runs to the next quote, and some rules reach across lines (a quoted value up to 1,000 bytes). Where it ran in, it would end where scrump resumes its scan, maybe inside a secret, past the key that marks it; a hit the rule's filter rejects masks nothing and moves the scan on all the same.
  - So the texts go as records, each scanned on its own (scrump's records mode, scrump 0.2.0 and later; tacit's `RedactRecordsContext`): no hit crosses from one text into the next. scrump reads one separator per text; tacit adds #84's repro to its first records call of the process, and masks a text holding a record separator in a call of its own.
  - A scrump without records mode refuses the flag, and one that takes it but keeps the repro's password does not keep texts apart; tacit does not ask either for records again in that process, and the run's result says once that texts went joined. The texts then go joined into one text by a boundary that closes an open quoted value, is longer than the text profile's longest reach across lines, and ends with a mark no secret's value starts with, and are cut back at the same offsets: masks keep the length. A text masked from its first byte all the same (a rule longer than the boundary) is masked again on its own, and a byte stays masked when either call masked it.
  - When redaction cannot run, nothing is read and the source fails. When it fails on a batch, each file in it is masked on its own; the file it fails on stores nothing past its cursor this run and is named, and the next run takes it up there.
  - The reader's saved state (`file_cursors.state`) holds transcript lines as they are, unredacted: a Codex question's options, a local command's caveat, the cwd. tacit's rules need them whole. It is as private as the transcript, in the same 0600 store, and is never printed, exported or sent.
- **Cursors.** Each transcript has a cursor: the offset after the last line stored, and the reader's saved state, so following a growing session reads only what was added.
  - A file is told from a new one by its inode and a fingerprint of its first line, as the mistakes log is. A file the harness compressed in place keeps its cursor, since tacit names offsets in the decompressed bytes. A compressed copy is final and keeps no state.
  - A transcript is read, redacted and stored 64 MiB at a time, with each batch's events and cursors in one transaction. Only the part that ends a read marks the file as read: a run that stores a part but not the rest reads on from the cursor next time. An unchanged file is not opened.
  - A file cut or replaced is read again from its start. Its events at places the new content does not reach stay. A file rewritten in place, with the same first line and grown past its cursor, is read on from the cursor: tacit's saved state sees the change and makes the read pass over the lines before it, but the lines it changed there are not stored again. Harnesses append, so both are rare.
  - A file whose plain and compressed copies are both gone loses its cursor and keeps its events. A run that could not list a source keeps every cursor.
  - A Hermes session's cursor is its last row's id. Hermes writes new rows on /retry, /undo and /compress; a row it rewrites in place keeps the version first read, until a schema step reads every source again.
  - OpenCode is mutable: a changed session is reread, with its messages' own keys. Events and the session fingerprint commit through the same redaction writer. A failed batch leaves no final fingerprint; the next ingest reads the session again. Deleted source rows leave kept events, as deleted transcripts do.
- **Kept.** Claude Code deletes a transcript after about 30 days, so its events can be all that is left of it. A schema change migrates them and never drops them (Store).
  - `evidence rebuild transcripts` refuses without `--force`. With it, it says how many of the events it dropped have no source left: those the next ingest of the configured homes and additional native sources cannot read again. That is a transcript it does not find (including a compressed copy or an archived Codex rollout), or a Hermes/OpenCode session no configured store holds. With neither homes nor additional sources, every event. Lines past a cut and rows a harness took back are lost too, and not counted.
  - The cursors and the reader's saved state are derived: a schema step that reads again drops them, and the next ingest reads every transcript still there again from its start.
  - Reading again stores nothing twice of a transcript that is only appended to. An item's key names its record (a transcript's line by its offset, a Hermes row) and its place among the record's items, and a record read again holds that reading's events only. tacit reads the prompt history as it is when it reads, so a turn whose pastes it now cuts otherwise numbers its items otherwise: the old cut's events are dropped, not kept beside the new.
  - Reading again has limits, so a step reads again only when it must. A transcript rewritten in place with lines that moved stores them again at their new offsets; the cursor path reads such a file on from its cursor and stores nothing twice. A record that now gives no item keeps the events it had. And each item is credited as tacit credits it when it reads again: a turn whose paste the prompt history no longer records reads as his whole.
- **Prior art.** OpenTelemetry's filelog receiver gave the cursor rule. Two event formats were not followed:
  - OpenTelemetry's GenAI conventions (in development) record messages with the model API's role. A role says which side of the API a message is on, not who wrote it: a prompt that another agent or a wake loop typed is `user` too.
  - Claude Code's own OpenTelemetry events (`user_prompt`, `tool_result`, `api_error`) leave prompt text and tool input out by default. They begin when telemetry is turned on and cover one harness. The transcripts already hold every harness's history.

The incidents source keeps one event per incident, rewritten as its file changes: its status, its last sighting and its running count of repeats. Each change of the last sighting or the count is also a sighting, an event of its own (kind `incident-seen`, keyed by the incident, its last sighting and its count), with the repeats since the sighting before: what the incident did over time. Times compare at the store's millisecond, so a file that writes microseconds files no sighting again; a change of anything else (a note, the status, the attempts) files none. A first sighting holds the whole count and carries when the incident was first seen. The sightings are kept: `evidence rebuild incidents` drops them only with `--force`, since the files keep only the running counts.

`momentum evidence events --session ID` prints one session's events, with its subagents' among them, oldest first, from its start; `--since` and `--until` take a WHEN, as every command that takes a time does: a duration ago, a local time (`2006-01-02T15:04` or `"2006-01-02 15:04"`, seconds optional, or a date) or a time with its offset (RFC 3339, or git's iso date `"2006-01-02 15:04:05 +0300"`); a command that takes no arguments refuses one, most often a spaced time the shell split for want of quotes, and a listing the limit cut says so. `--harness NAME` prints one harness's events from every source.

## Store

One SQLite file, `~/.local/share/momentum/momentum.db`, mode 0600.

Writable and read-only opens URI-escape the filesystem path. A `#`, `%` or `?` in a filename stays part of that name, not a URI fragment or option. Two paths open separate stores.

- **Kept tables** hold what cannot be read again: every event, when each session entered its phase, the notes (Report), what the capacity runs observed (Capacity), the cases with their evidence, signatures and logs (Cases), and the loop's runs with what each spent (The loop, Record). A schema change migrates them and never drops them.
  - A kept table gains a column it lacks, with the column's default, and keeps its rows. SQLite's ADD COLUMN writes no row, so it costs the same on any table. The next column is one more entry in the store's list of columns: a NOT NULL column needs a default, and an added column cannot be a key.
  - A new kept table takes no step: it changes no row. A store from before it gains it at its next open, and a build from before it, which never reads it, keeps working on the store.
  - A change to their rows is a step: numbered, run once and in order in the transaction that opens a store from before it, and recorded in `schema_steps`. A step that changes what the sources derive (a column they fill, a fix in how they read) reads again.
  - Two triggers give Claude Code its one name as an event is written, by whichever build writes it. The repairs run in every migration, after the steps, and drop `events_source`, which an older build that opened the store makes again: a store that holds it is not current.
- **Derived tables** hold what the sources and the trackers derive from what they read: the cursors, the files parsed, the unparsed records, the transcripts' file cursors, the trackers' checkpoints. A step that reads again drops them, so the next ingest reads every source again from its start: a new column is filled wherever a source still holds what it read, and the events of what it no longer holds stay as they were. Other steps, and a column added with no step, keep them, and nothing is read again.
- The events of source `supervise` are kept like the sessions': momentum's own record of what it sent and why, which nothing can read again.
- `user_version` stays at 3. The last build before the events were kept drops every derived table, the events among them, when it is another number. Run on a migrated store, it finds its own version, reads on from its cursors and drops nothing; what it writes takes the one name as it is written, and the next open of a build since drops the index it made. A build from before version 3 drops every event but the sessions' when the number is another, and sets user_version below 3. The next open takes that version, whatever `schema_steps` says, and runs the steps again, so the step that reads again brings back what the sources still hold. A store at a step newer than the build's is refused and left as it is.
- **Harness names** are one spelling in every source: claude, codex, pi, hermes, opencode, grok and kimi. The sessions layer has native scanners for the first five. Schema step 5 keeps every event and drops derived cursors, so retained results are reread with failure status inferred before clipping.
- **Prior art.** SQLite's rules for ADD COLUMN set what a step can add. golang-migrate numbers its migrations, runs them upward in order and records the version in a `schema_migrations` table; its down migrations are not followed, since a kept event has no way back. Parallel change (expand and contract) is why an older build keeps working on a migrated store while builds change over.

## Report

The report is how momentum shows its state. It adds no app, dashboard or notification: a view in a surface the owner already looks at (a section on his phone's radar page, one on his desktop dashboard's Today view) calls `momentum report --json` on its own schedule, keeps its last good copy, and draws the section in its own design. Nothing pushes and nothing tries to wake him; a view may badge what needs him.

- **The object.** One JSON object on one line: `version` (1), `generated_at`, five sections and their `counts`. A section is an array of items. An item has an `id` that stays the same from call to call, a `title` (one line of at most 120 characters), an optional `detail` and `effect`, an `at` (RFC 3339 in local time: when it happened, was decided or started), `links` (a label and an http or https address each) and a `source`.
  - `needs_you`: the decisions only the owner can make. Each title is the question itself, or what momentum could not do. Supervision adds one for each session that waits on its owner past the owner window (`supervise-ask:KEY`), and marks it done when the session moves on (Supervision).
  - `decided`: decisions made on his behalf that he may override; the detail says how. The last 12 hours. Capacity adds one for each run that deleted, offloaded or pruned, and one per disk for its last fast fill once it ended, which needs no one (Capacity, What a run leaves).
  - `shipped`: improvements that landed, each with its measured effect when there is one. The last 12 hours.
  - `running`: the work in flight, from the live session layer. Never from notes.
  - `problems`: what momentum saw and could not fix itself, which someone should act on. Supervision adds one when it gives up on a session (`store.SessionProblem`, one per session, added once per give-up: an add makes a note the owner resolved stand again), and marks it done when the owner comes back to the session or it works again. Capacity adds one for a disk that fills fast (until the fill ends) or is past its full percent, a run that held its deletions because it could not read what keeps an item (the processes, Docker, the live sessions, the scheduled jobs), a rule that could not run and a disk whose use it cannot read, a deletion that failed, and an item its rule would take that something outside the rule keeps, the uv cache once its prune has been held off for a day (Capacity, What a run leaves). What a rule leaves by its own policy, an excluded project's build output or Docker's volumes, is no problem: the run's events and its output hold it.
- **Plain text.** A view renders none of it as HTML or markdown, and none of it can act on a terminal or reorder what is shown: every text is one line, without control characters (escape sequences, bells, NULs) or invisible format characters (bidi overrides, zero-width spaces), the joiners of scripts and emoji kept. Running's text comes from what agents write, so it is made plain too.
- **Order.** Each array is sorted by importance, then newest first, and holds at most 20 items; `counts` counts them all. A note's importance is the one its writer gave it: high, normal or low. In running, the sessions that are working come first, then workflows, agents, and background jobs and monitors; the work of an automated run comes after all of them.
- **Notes.** The four sections other than running are notes, kept state that nothing derives: a schema change keeps them and `evidence rebuild` never touches them (Store). `momentum note add` writes one and prints its id. An id given again replaces that note and makes it stand again, so a writer that keys a note by what it is about (supervision keys its problem by the session) never adds it twice. The ids of running's items (`session:`, `task:`) are not a note's, and an id holds no space, control or format character and does not start with a dash. A writer that keys a note by a name it does not choose (capacity, by a disk's path) keeps a name an id may hold as it is, so its id never changes; in any other name it writes each character an id may not hold, each `%` and each byte that is not UTF-8 as `%XX`, one for each byte (`store.IDPart`). Two names that need the escape never share an id; a name that needs none shares one only with the name whose escape it spells out (`/mnt/a%20b` and `/mnt/a b`). `momentum note done` takes a note out of the report: it resolves a needs or problem note, and withdraws a decided or shipped one. A needs or problem note stands until it is done, a decided or shipped one for 12 hours. `momentum note list` prints every note and whether the report shows it; one past the 20 of its section is counted, not shown. Inside a sessions run, which holds the write lock, a note goes in the run's transaction (`Run.PutNote`).
- **Running.** The report makes the scan a sessions run makes, the same function, resumed from the checkpoints the last sessions run of the same build saved, so it reads only what each transcript gained since: on a store the sessions timer keeps, a report costs about what that run costs. It saves nothing (no checkpoint, stamp or event), takes no lock, and is safe to call every minute; what it saw, the next sessions run records. Running holds every session that is working, and every workflow, agent, background job and monitor a session has in flight, whatever its phase. A session's time is when its working stretch began, from the saved stamps; one that began working since the last sessions run is dated by the report's own clock until that run saves its stamp. A task's time is when it started.
- **Read-only.** The report opens the store read-only: it makes no store, migrates nothing and writes no row. SQLite may make the `-wal` and `-shm` files a reader of a WAL store needs, with the store's mode, and the next writer removes them. No store, or a store that is not this build's schema, is an error: the next sessions run, ingest or note of this build migrates it, and a newer build's store stays refused.
- **Exit.** 0 with the object. The look at the machine (the snapshot and every harness's scan) has 3 seconds, below the views' timeouts, and the harnesses are scanned at once, so one that hangs holds up no other. A harness that fails is named on stderr and running holds what its scan did read; one not done by the deadline is named too, and its sessions are left out. The report still prints, so the notes reach the views. A `sources.json` it cannot read is named on stderr too, and projects go unnamed. A report that cannot be made (no store, a store not this build's schema, no process table) prints nothing and exits 3, and the views keep their last good copy. Without `--json` it prints the same sections for a terminal.
- **Prior art.**
  - JSON Feed 1.1 gives each item an id that never changes and is never reused, keeps text plain outside one HTML field, and dates in RFC 3339. The report follows it, has no HTML field at all, and has fixed sections with counts in place of one list.
  - Waybar's custom module runs a command on an interval and reads the one JSON line it prints. The host owns the schedule and what it shows when the command fails, as the views do here.
  - `gh status` gathers what needs its user across every repository into fixed sections, in one command, for a terminal.
  - Calm technology (Amber Case) asks for the smallest possible amount of attention, the periphery before the center, and a usable state when the technology fails: no push, counts first, and a last good copy.

## Capacity

An empty `.git` directory is no repository. Ownership checks continue to the nearest Git metadata file or nonempty directory. Unreadable and broken metadata still hold deletion.

`momentum capacity` keeps the disks from filling, so nobody cleans by hand. The ingest timer runs it every 5 minutes. Each run samples which paths processes use and records each disk's use; then each rule that is due scans. A rule named in `live` deletes (scratch offloads too). One not named lists what it would do and does nothing. Every path is the machine's configuration, in the `capacity` section of `sources.json`; nothing is compiled in, and a key this build does not know is refused (a typo in `exclude` or `keep` would drop a protection without a word).

- **The sampler.** A filesystem mounted noatime never says when a file was read. So each run reads every process's open files, its memory maps, its working directory, its program and the paths on its command line (with the `org/name` words, which may name a Hugging Face repository), and keeps the paths under the rules' roots. A sighting under a models root is recorded in `capacity_seen` against its item, and one under a scratch root but no models root against its folder: first and last, how, and by which process. The other rules judge use at the run. A file opened and closed between two runs is not seen. Another user's processes cannot be read, and are counted. Root's are often a container's, so at each scan the host paths running Docker containers bind-mount count as used too: a mount of an item, or of a directory that holds a root, keeps every item under it and is a sighting of each. A Docker that cannot be asked (its socket's permission, a timeout; not one that is not installed or not running) makes the run delete nothing, with a problem note (`capacity:hold:docker`) that the next run that asks it resolves. Each run records its time, how long its sample took, how many processes it read, and whether it could trust its look (`capacity_runs`).
- **A look the run cannot trust deletes nothing.** In a PID namespace of its own (a sandbox, a container) the process table holds only the run's own processes. A table with no process, one without the run's own, or one far smaller than the recent runs' (under half the median of the last 24 trusted runs, once there are 12) is not the machine's either: every item would read as unused. The run then deletes and prunes nothing, says why in a problem note (`capacity:hold:look`, resolved by the next run it trusts), and its time does not count as watched.
- **One name per file.** A path reached through a bind mount names the same file as the path through the filesystem's own mount, and `/proc` shows whichever a process used. A path compared with a root, a use or a job's name is taken by its canonical name: its place on its filesystem, shown through the mount that shows the most of it (`/proc/self/mountinfo`). A path a job or `keep` names counts twice: as written, and through its symlinks. A Hugging Face snapshot's file resolves into the shared blob store, under no item, while its written path is under its repository.
- **What a job names stays.** A path named by a systemd unit (enabled, loaded in any state, template instances and transient units among them, or started by an enabled timer, path or socket), a crontab line, an enabled Hermes job, or an installed command's symlink (`names.links`) is never deleted, nor an item that holds it.
  - A unit names what its fragment and drop-ins say and what systemd expands from them (its commands, environment and working directory), and what it hands its program, one level deep: its EnvironmentFiles and the scripts its commands run.
  - A quoted path keeps its spaces, and a quoted assignment's value is a word too. A word relative to a unit's working directory (a path, or a bare name that is there), or to a `cd` before it on a crontab line (else the home directory, where cron runs a line), names what it resolves to.
  - A file of the user's own jobs (a user unit's, a crontab script, a Hermes job's script) that cannot be read makes the run delete and prune nothing, with a problem note (`capacity:jobs`) that the next run that reads them all resolves. A system unit's file the user cannot read (root's configuration) is a warning: like root's processes, it is the limit of an unprivileged run.
  - A repository script that no job runs names nothing.
- **What a process uses stays.** An item a process uses at the run's sample is kept. Just before the deletions the run samples again, Docker's mounts and the live sessions among it, and judges each item again: the same inode as when it was judged, no write since, and for a worktree the same commit, still clean and still a leftover, with no one at work in its repository. An item that holds a mount point (another filesystem, or a bind mount of another place) is only reported, from the judgment on: a deletion would reach past it. A model or a target dir is deleted through an `os.Root` of the directory it was found in, and a task folder's model data through one of the folder, so no symlink leads the deletion outside, and under an exclusive BSD lock on a directory: one another process holds a lock on stays (systemd-tmpfiles's convention). A worktree goes through `git worktree remove`, and a shared blob under Hugging Face's own lock.
- **Excluded projects are report-only** for every rule but models, and the model data in tasks' folders. A project is named by its paths, by a glob a component of a path matches (a renamed checkout, an alias, a lane's scratch folder, a lane's branch), and by its git remotes (owner/repo), wherever the checkout or worktree lives. A repository is placed at its main checkout, or at a bare repository's own directory (a hub some lanes keep). A path under a root that is a link, or under one (an item, a target's source, a repository's main checkout), is matched as the configured root spells it too, and a target's sources also as Cargo wrote them: a glob may name only the alias.
- **MinMiB** (1 MiB) is the smallest item the models and targets rules delete, and the smallest file of model data the scratch rule deletes: a smaller one frees nothing, and the small entries at the top of a cache are its markers, locks and credentials.
- **What a deletion frees** is the space of the files whose last link it removes, their blocks as `df` gains them, and of the directories it removes. A file with more than one link counts only when every other link to it is among the paths the run deletes, each inode once in the item and in the run: a wheel a project's environment still links, or a clone's object its source still links, frees nothing. The paths are what the rule deletes: a model with the shared blobs and manifests it is the last to link, a target dir's own entries, a worktree with its administrative directory (`git worktree remove` takes it too), a task folder's model data and then what its offload removes (what restic's repository grows by is not counted, on whichever disk it is), and what a prune around running environments removes. Each deletion counts the paths' links just before it and what is left of them after it, so a link an earlier deletion of the run took is gone by then, a deletion that stopped midway counts what went, and another writer on the disk counts for nothing. For each item a judging rule would delete, a dry run, and a judging rule not live, says what its deletion would free: its links as the rule judged them, after what the run's own deletions took, in the order the run deletes, each file counted with the deletion that takes its last link; an item inside one deleted before it frees nothing more, one that holds one is counted again without it, and one that holds or is inside a deletion that stopped midway is counted again as it is. A prune done by a tool (uv's own, Docker's) has the tool's own figure, named as the tool's. A block a clone shares with another file (a reflink, on btrfs or XFS) counts as freed: nothing in a file's links says another shares it.

The rules:

- **models: models, datasets, model caches and run checkpoints.** The owner's ruling: they are downloaded or made again when work on them resumes. An item is a top-level entry of a configured root; a root inside another is a container, its own entries the items. An item that has had no write (no modification or status change of any entry) and was not seen in use for 30 days of watching (`idle_days`) is deleted, never archived.
  - Watched time counts from the latest of the item's newest write, its last sighting, and when the sampler began to watch its root (a mark the first run that watches the root sets; a run that records without it clears it, so a root added back starts again). A sighting counts when it is of a path in the item, of a shared blob it links, or of a key above it from before a root was added inside another. Only runs that could trust their look count, and a gap between two runs counts for at most 30 minutes: time the sampler did not run (the machine asleep, a broken timer) is not idle time. So nothing goes before the sampler has watched its root for 30 days, and a root added later waits its own.
  - Items in `keep`, or that hold a kept path, stay; so does a repository a named or kept path's blob is linked by. Excluded projects do not apply: the owner ruled on models directly.
  - A Hugging Face cache keeps the files Xet downloads once, in a store shared by its repositories (`<cache>/blobs`, marked `.huggingface-shared-blobs`), and a repository's blobs link into it. The store is never an item; a store whose marker names a layout this build does not know (it knows `1`) leaves the repositories that link into it alone. A repository counts the shared files only it links (a repository in `keep` links its own too), a process that maps a shared file uses every repository that links it, and a repository named on a command line (`org/name`) is in use.
  - The last repository to go takes a shared file. As Hugging Face does, it holds the file's lock (`<file>.lock`) while it reads the file's manifest (`<file>.refs`) and unlinks the file and the manifest, only when the manifest names no link that still resolves to the file. The lock file stays, and a file is kept on any error but a missing one.
- **targets: Rust build output.** A Cargo target directory (Cargo's `CACHEDIR.TAG` and its `.rustc_info.json`; Cargo's registry cache has the tag, not the file) that has had no write for 48 hours (`idle_hours`), that no process uses and no job names, and that git does not track (it ignores it, or it is in no repository) is deleted: Cargo builds it again.
  - Its project must be known and not excluded: the repository it is in, and every source its dep-info files (`<profile>/*.d`, `<profile>/deps/*.d`) say it was built from, each file read whole. One with more than 20,000 dep-info files, or one longer than 4 MiB, is of an unknown project. One of an excluded project, one whose project is unknown (in no repository, and no source of it in one), one git does not ignore, and one git cannot say it ignores (git fails on the repository, does not run, or does not finish) are only reported.
  - What Cargo does not build again stays (Criterion's saved baselines, a build script's downloads): of a target dir that holds such entries, only Cargo's own go (its profiles, target triples, `doc`, `package`, `tmp`, rust-analyzer's flycheck dirs, its tag and info files).
- **worktrees: leftover worktrees.** A linked worktree under the roots (globs) is left over when its branch, pushed under its own name, is merged into its remote's default branch (as the remote-tracking branch knows it), its changes are all there already (a squash merge, a cherry-pick: merging it would change nothing), or it is gone from its remote (`git ls-remote`).
  - It is removed with `git worktree remove` when it is clean (no change, no untracked file, no ignored file but a rebuildable cache, no file marked skip-worktree or assume-unchanged, whose edits status hides) and its commits are merged, landed, or on a branch its remote has now, at the commit `ls-remote` gives for it: a remote-tracking branch the clone kept after the remote deleted or rewrote the branch proves nothing. Its branch goes with `git update-ref -d` at the commit it was judged at, so a branch that moved stays. A rebuildable cache is a tagged cache directory, `node_modules`, Python's caches, a `.venv` and the like; a Cargo target that holds what Cargo does not make (Criterion's baselines) is not one.
  - One with uncommitted, unpushed or ignored work is only reported. A worktree a process is in, one changed in the last hour (an agent finishing after its merge; a change as the next bullet counts it), a locked one and an excluded project's are left; the excluded project's leftovers are reported.
  - One whose repository someone works in is left too: a process's working directory or a live agent session (in any phase but done) in any of the repository's work trees, or a change to one of them in the last hour. A look at the sessions that is not whole leaves every worktree it would remove on that run (`capacity:hold:sessions`). An agent between two commands runs nothing there, but its last command left a change: an entry made, removed or renamed in one of the tree's directories, git's index or HEAD, or a new entry in HEAD's log (an add, a commit, a checkout), read from the tree's git directory wherever it is kept. A fetch writes only under `.git`, and a gc rewrites HEAD's log with its entries kept, so neither is a change; a bare repository has no tree to change. Nor is capacity's own deletion. Each deletion records when it went and, for each directory it changed (the path, and the directory it was in; for a task folder's model data, the directories its files were in too), that directory's last change before it that was not capacity's. A directory whose change is no later than such a deletion (this run's, or one recorded in the last hour) counts by that earlier change, against each run's own window: someone's change stays a change, though the deletion hid its time. The scheduled-AI policy leaves a repository another agent or a human works on alone, so its branches wait for a run after the work stops.
  - A branch never pushed under its own name (a new one that still tracks the default branch), one never committed to (its reflog holds only its creation) and a detached worktree are work in progress, not leftovers. Git runs without optional locks, so a status never refreshes the index another session uses, and never prompts.
- **scratch: tasks' folders in the cache directory.** The machine's rule is that a task keeps its scratch in a folder of its own there and removes it when it closes; many do not. A root's top-level folders are tools' caches and tasks' folders, and nothing in a folder says which.
  - A folder is a task's when an agent made it: a tool call of an agent's in the store's transcripts creates it, from ten minutes before the folder's birth (statx) to ten minutes after. A call is recorded as it is issued, and its command may make its output minutes later; a call that adds to a folder made by a command this rule cannot read (a script's heredoc) comes minutes after. The call names the folder as a whole name that starts a word (after a space, a quote, `=` or a separator; not after a host's `:` or inside another path), through the root as configured, its canonical path, `~`, `$HOME` or `${HOME}`. What creates it is a list of what makes a directory, so a call this rule does not know makes nothing. A command is read with the values of the shell variables it assigns put where it uses them, up to the next assignment (`S=P; mkdir -p "$S"`; 8 KiB at most), past the shell's keywords (`then mkdir`), in a shell tool's command or an exec tool's (in quotes or a template literal):
    - a command that makes it: `mkdir` (and `mkdir -p` a path inside it), `install -d`, `git clone`, `git init` or `git worktree add` (which make parents too), or the destination of `cp`, `mv`, `rsync` or `scp`, the folder itself;
    - a command that hands it to a program that makes it: after a long option whose words name such a directory (`--output-dir`, `--cache-dir`, `--local-dir`, `--log-dir`, `--target-dir`, `--prefix`, `--dest`; not `--output` or `--checkpoint`, which name a file), unzip's `-d`, wget's `-P`, curl's `-o` with `--create-dirs`; or as a directory variable the program makes (`HF_HOME=`, `UV_CACHE_DIR=`, `CARGO_TARGET_DIR=`, `OLLAMA_MODELS=`; not `TMPDIR=`), before the program or exported;
    - a script that makes it, by the name or by a variable that holds it: `os.makedirs("P`, `fs.mkdirSync("P`, `mkdirp("P`, `out = Path("P"); out.mkdir(`, `D = "P"; os.makedirs(D`; `os.mkdir` makes only the folder itself, and a `Path`'s `mkdir` a path inside it only with `parents=True`;
    - a call that writes a file in it: the path of a `Write`, `write_file` or `create_file` call, a patch's `Add File`.
  - Its output counts only when it says it made directories (`"dirs_created": true`), or when its call ran `mktemp` and it names the folder itself (mktemp makes no parents). Nothing else makes it: a test (`[ -d P ]`), a listing, a read, a deletion, `cd`, `tar -C` (which needs the directory), a listing's output, the owner's own commands, and a name the store cut (it keeps 240 bytes of a call and marks the cut with an ellipsis). So a tool that makes its cache again after an agent removed it, or that an agent then tests for or lists, made it itself. A name past the cut is not read, so its folder is no task's: the rule errs toward keeping.
  - These are never a task's: a folder tagged as a cache (the Cache Directory Tagging Specification's `CACHEDIR.TAG` at its top, which a Cargo target dir has too), one named like an installed command (in `names.links` or on PATH), a configured root or one that holds one, a linked worktree, a link, one with nothing in it, and one whose filesystem keeps no birth. They are left alone. A task's folder beside its pointer (`NAME.restic.txt`) is only reported: an offload left it, or it was made again, and another offload would overwrite the pointer.
  - A task folder is idle when it has had no write (a modification or status change of any entry) and no sighting for the window, in watched time as the models rule counts it, from when the sampler began to watch its root.
  - Its model weights, checkpoints and datasets go as the models rule's items do, after its idle time (30 days), never into restic; a file of it in the models rule's `keep` keeps the folder whole. A folder whose model data the run cannot remove (a directory of it the user cannot write, as a container running as root leaves) is only reported: its model data cannot go, and the rest cannot go to restic with it. They are its files of at least `min_mib` named `.safetensors`, `.gguf`, `.ggml`, `.pt`, `.pth`, `.ckpt`, `.distcp`, `.onnx`, `.tflite`, `.parquet`, `.arrow`, `.engine` or `.trt` (TensorRT), TFRecord and MosaicML shards (`.tfrecord`, `.tfrecord-00000-of-00001`, `.mds`, compressed or not), a TensorFlow checkpoint's shard (`.data-00000-of-00001`), a Megatron dataset's `.bin` beside its index, or whose first bytes are GGUF's, legacy GGML's, safetensors', a PyTorch archive's (a zip whose first entry is its `data.pkl`), Parquet's, Arrow's or a Megatron index's: an Ollama or Hugging Face blob is named by its hash. What a run's results are often kept in (JSON lines, CSV, NumPy and HDF5 arrays, pickles) is left to the offload, and so is what a tool installed or builds: an environment's packages, `node_modules`, a Python environment, git's store, a Cargo target, a tagged cache but a Hugging Face hub.
  - The rest is offloaded after 21 days (`idle_days`) with evidence-offload (`offload`, tagged `tag`): restic keeps the folder, the folder goes, and `NAME.restic.txt` in its place says how to restore it. Nothing else of it is deleted. A folder with model data waits for the later of the two times; then its model data goes and the rest is offloaded at once.
  - It stays while a process uses it, a job names it, it is in `keep` (or holds a kept path, or is inside one), a live agent session works in it, a session that made it is still open, or a repository references it. A live session is the one that made it when its harness's id for it is the id the call's transcript carries: Claude Code's session id (a background job is keyed by its job), a Codex thread, a pi or Hermes session. The sessions are asked only about a folder that would otherwise go. A look at them that is not whole (no snapshot of the machine, a harness that failed or ran out of time) keeps such a folder on that run, with a problem note (`capacity:hold:sessions`) the next whole look resolves. A repository references it with a worktree in it of a repository elsewhere, a worktree elsewhere of a repository in it, or a remote, alternates or worktree that a repository the shared walk finds (a checkout's `.git`, a bare repository) has in it. A file in a repository that names the folder does not keep it; a job that runs the file does.
  - An excluded project's folder is only reported: by its place, by the remote of a repository in it, or by where a session that made it worked then: that place, or the repository there (its remotes, and the place of a worktree's repository) as the rule's first look at each of the folder's makers saw it or as it is now, since a lane removes its checkout when it closes (an excluded project's lane keeps its scratch in the cache too). The look is kept for the folder's birth, so one made again under its name is looked at again. A folder a session made in a directory that was gone when the rule first looked is of no known project: only reported, but its model data, like an excluded project's. Its model data still goes, as the models rule's does. One that holds a mount point is only reported, and so is one with a directory the run cannot list or search: what it holds is not known.
  - Before each folder, the run looks again at the processes, Docker's mounts and the live sessions (an offload takes minutes, so the look before the first is old by the second), and judges the folder again: the same inode, no write since, no process using it, no live session in it or of it. It opens the folder and checks it is the directory judged (evidence-offload resolves its argument, so a directory swapped in would be the one offloaded), and takes an exclusive BSD lock on it. It deletes its model data through an `os.Root` of the folder when every file is still the inode judged, else none. What it deleted is on record (with the directories it changed) before anything else happens, a deletion that stopped midway too. Then it runs the offload.
  - evidence-offload is the machine's script, not this repository's. It takes one directory, resolves it (`readlink -f`), makes its entries the user's and readable (`chmod -R`, `chown -R`), backs it up to restic with the tag in `EVIDENCE_TAG`, writes `DIR.restic.txt` beside it (the snapshot and how to restore it), removes it, and prints `snapshot ID`. restic reads the folder as it goes, so what is written to it during the backup may be lost. An offload that leaves the folder in place, or no pointer, is a failure; one that failed but left its pointer and no folder went, its snapshot read from the pointer. An offload has 10 minutes (restic backs up new data to a local repository at a few hundred MiB/s, over 100 GiB in that time); then it and every process it started are stopped (it stays in the run's process group, so a stop from the terminal reaches it as it reaches the run), and its output is waited for 5 seconds more. A folder whose offload ran out of its time is only reported until it is smaller. A failed offload restarts the folder's idle time: the script changed the modes and owners of its entries. Nothing is removed before the backup is done, so a stopped offload leaves the folder whole, or backed up with its pointer beside what is left. A run starts offloads for 4 minutes at most, since the next run waits 5 for its lock; the rest wait for a later run.
- **uv: the uv cache.** `uv cache prune --ci` when the cache is over 30 GiB (`max_gib`), or 7 days (`every_days`) after the last prune. `--ci` drops the wheels uv can download again and keeps the ones it built.
  - Every prune, `--ci` or not, also deletes every environment uv keeps in its cache: a `uv run --with` layer, a `uv run --script` script's, and that of a tool `uvx` (`uv tool run`) runs without installing it. A process running from one fails its next import. One running from an environment outside the cache whose files are hardlinks or copies of the cache's (a project's `.venv` or an installed tool's, in uv's default link mode) is untouched; one whose packages are links into the cache (uv's `symlink` link mode), or whose environment is itself a link into it (a centralized project environment), is not. (On a copy of a cache, a forced prune broke the first three kinds, under uv 0.12 and 0.13, and left the other two working.) A prune also deletes the buckets of another uv version that shares the cache, its built wheels among them. uv keeps a cached environment (a tool uvx runs, a `--with` layer) in `archive-v0` beside the unpacked wheels, with a link to it in `environments-v2` by its interpreter and its requirements; a script's (and a centralized project's) in `environments-v2` itself; and a temporary one in `builds-v0`: the overlay a `uv run --with` runs its command in, whose `.pth` names the layer and the environment beneath, an isolated run's, and a script's without dependencies.
  - Every uv process holds uv's lock (the cache's `.lock`) shared for its whole life, whatever it runs. A prune without `--force` takes the lock exclusively: it waits for every holder (`UV_LOCK_TIMEOUT`) and then gives up having removed nothing, and while it waits a new uv process still starts.
  - So the rule looks first. A uv process is one whose program is `uv` or `uvx`, alone or with a suffix that starts with an `@` or a version (`uv@0.13.5`, `uvx-0.13`: uvx runs the uv of its own suffix), and its command is the first of uv's commands (hidden ones and aliases among them) on its command line, past the global options and their values. A `run`, `tool run` or `uvx` has started its command when it has a child with the environment uv gives its command: `uv run` counts `UV_RUN_RECURSION_DEPTH` up, and `uv tool run` puts its environment's `bin` first on uv's own PATH. A child with uv's own environment is a helper uv runs on the way (the libc probe, a keyring, git, nvidia-smi), and one with `UV_INTERNAL__BUILD_DIR` is a build backend. A child with no PATH where uv has one is the command, its environment since replaced: a command that set its process title over it (setproctitle does), or an `env -i`. It is judged by its files, but under a `uv run` that layers one of the cache's environments over its own (`--with`, `-w` alone or among short flags, `--with-editable`, `--with-requirements`, read among uv's options up to its command, since every word after the command is the command's own) it imports from the layer with no file of it open or mapped, and what it maps may come from the environment beneath: it uses the cache, and a prune around it keeps the overlay it runs in (below), which names the layer. The rule waits quietly for one that may write the cache now: an install, a sync, an add or remove, a lock or an upgrade, a venv, a clean or a prune, and a `run`, `tool run` or `uvx` that has not started its command (it may still be building its environment); a quiet wait for one process that lasts a day is reported instead, since no install takes that long and the rule cannot tell what such a process runs, and so is every quiet wait once the prune has been held off for a day, whatever held it (What a run leaves). A process uses the cache by a path in it other than the lock file (a program, a mapped or open file, a working directory, an argument), by the program it was started as (a cached environment's `bin/python` is a link to an interpreter outside the cache), or by its environment (uv starts a command with the environment's `bin` first on PATH, and a script's with VIRTUAL_ENV, and its children inherit them; PYTHONPATH may name a place in it too), an environment in the cache once its links are resolved or with its packages linked into it, and one started as such an environment's `python`, whatever its name (a project's `.venv` that links into the cache). The prune goes around such processes (below). It waits, and names them in a problem note, for those whose use of the cache it cannot tell: one with `UV_LINK_MODE=symlink`, whose packages may be links into the cache wherever its environment is, and the ones that follow. A place that does not answer in 2 s (a dead network or FUSE mount) counts as one in use, and the note names it; on local disks a place takes milliseconds. The cache and its lock file are matched as uv names them and with their links resolved, where `/proc` shows them. It waits too for a holder of the lock it cannot read, or one with a process under it whose open files or environment the run may not read (another user's), or that runs in another mount namespace and does not see the cache's lock file where the run does (`/proc` gives its paths as its namespace names them), and for a running Docker container that mounts the cache, a directory in it or one that holds it. The holders come from `/proc/locks`, read before the look, the holders of a lock file an earlier swap replaced among them (a process still has it open, and `/proc` names it deleted), so a holder that the look does not show and `/proc` has no more has ended, unless `/proc` hides other users' processes (`hidepid`), when it is one the look cannot read. Under any `hidepid`, a holder's process tree has every child the kernel lists for it (`task/TID/children`): one the look does not have is one it cannot read. `/proc/locks` names a file by its filesystem's device, which mountinfo gives too; `stat` gives the same one but on btrfs, which gives each subvolume a device of its own.
  - Otherwise it prunes: with uv's prune when no process uses the cache, no scheduled job names a place in it and no command may run in an overlay of `builds-v0` unseen, and around them otherwise (below). With no holder, it runs uv's prune without `--force` and uv's own lock decides. With holders that are all a `run`, `tool run` or `uvx` past its sync, and no process waiting for the lock or holding it alone (a clean or a prune, which would get the old file once its holders end, while new processes run on the new one), it puts a lock of its own in the lock file's place: a new file, locked exclusively, renamed over `.lock`, when the lock file is still the one the look saw. Just before the rename, with its lock taken, it looks at the processes again (each holder that still runs runs the command the look saw, and no process uses the cache, or, around running environments, what the first look did not keep), then reads the open files and then the locks (uv locks the file as it opens it), and gives up without renaming, every holder on the file in place, on what the look finds, a holder the look did not see (by its pid and its start), a process waiting for the lock or holding it alone, one that has the lock file open and was no holder (uv opens the file, then locks it), or a uv process the look did not see whose open files it may not read. A uv process that starts during the prune opens the new file and waits, as it waits for uv's own prune, up to its `UV_LOCK_TIMEOUT` (300 s by default), then fails; the holders keep the file they hold, whose lock protects nothing the prune removes. After the rename it looks the same way again, for what came in the moments between; what it finds then keeps its own prune from running. Before uv's own prune the holders run outside the cache, and the new file stays in place after it, with a process that came to the old file in the instant before the rename: a lock no later clean or prune waits for. Around running environments the holders may run from the cache, and uv's own clean or prune must wait for them again: the old file stays beside the new one, a second link to it (`.lock.capacity-old`; uv's prune would delete it), and goes back in the lock file's place before capacity lets its own lock go, the prune done or given up. A uv process that came to capacity's file meanwhile then goes on under it: a lock no later clean or prune waits for (the rule's own looks still see it, by the deleted lock file it has open). One that waits for capacity's file to hold it alone (a clean or a prune) would run while the holders run from the cache, so capacity keeps its lock until that one gives up: its own `UV_LOCK_TIMEOUT` as uv reads it (whole seconds; anything else, or none, is uv's default, 300 s) and 10 s more, and 5 minutes and 10 s at most, since the run holds every rule while it waits. Past that it lets go, and says that the clean may run while processes run from the cache. uv opens the file, tries it without waiting, then waits for it, and between the two it is on no line of `/proc/locks`: capacity reads them 100 ms after the rename back, and waits too while a process that has its file open neither holds it nor waits for it. The uv processes that came to capacity's file before it wait as long, and may give up. A stop (SIGINT, SIGTERM, SIGHUP) that comes while the old file is aside ends the moves, and the run once the file is back and no clean waits for capacity's. A run killed in that time leaves it aside: every scan with the rule live puts it back, a prune due or not, on a run that may not prune too (it deletes nothing). It takes the file in its place alone without waiting, renames the old one back and waits out a clean that waits for the file it took, as above; while a process holds the file in its place, it waits. One killed before its rename left a second link to the file in place, which just goes. That look reads `/proc` and the lock files `/proc` names, counts an environment or a mount namespace no look read as in use without reading it, and has 10 s: a filesystem that does not answer must not keep every new uv process waiting, and past that time the rule lets its lock go and reports. uv's prune runs with `--force` and holds the file that holds capacity's lock, so the lock lasts while either of them runs, or the prune around running environments moves aside under it; then capacity lets its own go. The prune's time is in its record, failed or not, so a long one shows.
  - Around processes that run from the cache, the rule deletes the cache's entries itself: uv's prune cannot keep an environment. An environment's files are clones, hardlinks or copies of the unpacked wheels (uv's link mode falls back from clone to hardlink to copy), so the wheels can go while it runs; uv takes a pointer to an archive that is gone as a cache miss, and unpacks or downloads it again. The rule keeps the entry of `archive-v0`, `environments-v2` or `builds-v0` each place of the processes is in, and each one a scheduled job names (by its path, or through the nearest directory above it that resolves into the cache; a job that names the cache, a bucket or a path in another bucket names no environment): the place with its links resolved, or, when that leads out of the cache, the nearest directory above it that resolves into it (an environment's `bin/python` links to an interpreter outside; a place in a link of `environments-v2` is in the environment it leads to). It keeps the overlays of `builds-v0` a command may run in unseen (below), the links to the cached environments it keeps, and every entry a kept one reaches: a link's target (uv's `symlink` link mode links a package's files to the wheel's), a path a `.pth` file of its site-packages names (on a line, or as a string in a line that starts with `import`, as uv's overlay names them), the sources an editable install's finder module maps, `home` and `extends-environment` in its `pyvenv.cfg`, and the interpreter a script in its `bin` names. `builds-v0` stays whole for uv's own prune, which removes it: uv removes an entry as the build or run that made it ends, and one whose uv was killed may be the overlay its command still runs in, which that command names nowhere once it set its title over its environment (on a copy of a cache, uv's prune broke such a command). So an overlay there (its site-packages holds `_uv_ephemeral_overlay.pth`, its `pyvenv.cfg` names `extends-environment`, or its `pyvenv.cfg` cannot be read) keeps uv's prune from running, and what it names, while a command may run in it unseen: a process whose environment holds no PATH, that runs the interpreter the overlay's `home` names (any, under a `uv run` that layers one), and that started after the overlay was made (by its birth, where the filesystem keeps one), in this boot. An overlay no such process can run in holds nothing, and uv's prune removes it; another entry (a build's environment, an isolated run's) holds the extension a titled command maps, which names it. With such a process, a `builds-v0` the run cannot read is waited for. While processes run from the cache, a scheduled job names a place in it (for as long as the job does), or a command may run in an overlay unseen, uv's own prune does not run, and what only it cleans stays: the finding says how much of the cache that is. A process's environment outside the cache whose packages link into it keeps what they reach, and so does one a kept entry names (the base an overlay names, in uv's `symlink` link mode, which `link-mode` in uv.toml sets with no `UV_LINK_MODE`); a place in another bucket keeps nothing, and nothing of it goes. It waits, and names it, for a process that uses the cache or one of those buckets itself (a working directory there), a directory of a kept entry it cannot read, and a walk of what they reach that does not end in 30 s.
  - The rest of those buckets goes under the cache's lock: uv's own, taken alone without waiting as uv's prune takes it, when no uv process holds it, or capacity's in the lock file's place (above) when its holders are all runs past their sync. The looks under the lock let it go on a process that came to use what the first look did not keep, and, read from the cache last, on an entry of `builds-v0` the first look did not see. They judge a place the first look did not answer by its name: one in an entry it kept is fine, and so is one in another bucket that `/proc` gives with its links resolved (an open file, a working directory); one that a command line or an environment names in another bucket is not, since a wheel's pointer there leads into `archive-v0`. An entry of `archive-v0`, and of `environments-v2` an environment, is moved whole into `.capacity-trash` through an `os.Root` of the cache, with an exclusive BSD lock on it: it leaves uv's names at once, and is deleted once the lock is gone, since nothing reaches it there. A link of `environments-v2` to a cached environment that is not kept, or to none, goes as it is (a directory of links goes once it is empty); what is none of these stays, and so does a name in `archive-v0` that starts with a dot. An entry a job names or that holds a mount point stays, and is named. A directory the user may not read or write is made so, as uv does before it deletes, and its move runs again; what cannot be deleted is tried again at each later live run. What a run stopped midway moved aside is deleted at the next live run, prune or not, and that deletion is in no note. uv's own prune removes it too, as no bucket of its own. First, the files of `files-v0` that nothing links any more go, as uv's own prune removes them: uv 0.13's content-addressed cache (a preview) keeps a wheel's files there and hardlinks them into its archive, so those an archive moved aside alone linked go at the next prune. The other buckets (the wheels' pointers and metadata, the index, the built wheels, git, another uv version's) stay for uv's own prune. It moves no entry aside 4 minutes after the lock went in: a uv process that starts meanwhile waits for the lock up to its `UV_LOCK_TIMEOUT` (5 minutes by default), and what is left waits for a later run. An entry that cannot go is a failed deletion of its own, and the rest go. The finding says how many processes run from the cache (each named by the uv process it runs under), the jobs that name places in it and the overlays a command may run in unseen, how many environments it keeps and their size with what they reach, and `builds-v0`'s apart, what went, and how much of what stays is in `builds-v0` and the buckets it leaves to uv's own prune.
  - What a prune around running environments freed is counted as every deletion's is: what it moved aside, the files of `files-v0` and the links it removed, but the directories its moves made. What went out of the cache, its size before less its size after (uv's count, or a walk where uv gives none), is said apart: most of it may still be linked from environments outside the cache. What uv's own prune freed is uv's figure as its report prints it (`Removed 412 files (48.0KiB)`; since 0.12.6 uv counts a file as it removes it, when that removes its last link), named as uv's, `at least` where uv says so; a summary with no figure is uv's zero (uv before 0.12.6 prints none then). A report with no summary leaves the prune named by what left the cache, with that uv printed no total.
- **docker: Docker's caches.** `docker builder prune --filter until=168h` and `docker image prune` (dangling images), once a day. Volumes no container uses are only reported: one may hold a database. The build cache's size is what the prune removes, record by record, read from the builder the prune runs on (`docker builder du --format json`; `du` ignores an age filter): a record no build uses, that no image shares, that is not BuildKit's own (internal and frontend records, which a prune without `--all` keeps), last used longer ago than the age, and whose every child goes too (a child holds its parent, and a parent's own last use stays old while its child is used). Docker prints the last use rounded; the rule reads it at the least it can be. A record an image shares frees nothing while the image stays, and most of an old cache often is one. With nothing to remove, the prune does not run; a size that cannot be read (`du` fails, or prints a line this build cannot read, which may be the child that holds an old parent) runs it anyway, since it is Docker's own and limited by age. What a prune freed is what Docker prints it reclaimed, named as Docker's: its store is root's, which the run cannot count.
- **disk: each disk's use**, at every run (`disk_samples`). When a disk fills faster than 20 GiB an hour over the last 30 minutes (at least 10 minutes of samples), or would reach 94% within 6 hours at that rate while it fills at least 1 GiB an hour (`min_gib_per_hour`, a twentieth of the fast rate: a slower creep is the full note's, at the line), the run names the processes that write: those that wrote at least 1 MiB a second at a look of a few seconds (`write_bytes` read twice), and those that wrote since the last run that could trust its look at least the slowest rate the rule reports (`min_gib_per_hour`). A writer in bursts (a training run that saves checkpoints between two looks) is idle at a look.
  - Each run that can trust its look records every process's `write_bytes`, parent and start (`capacity_writes`), with which boot and when on its clock, read before the look lists the processes (`capacity_snapshot`). The same process (pid and start, on the same boot) wrote the difference. One that started since wrote all it wrote, and so did every process after a reboot. A counter that went down is not known.
  - A process takes in all a child wrote when it waits for it, and a launcher passes its children's writes on when it ends. So a process that ended shows in its nearest recorded ancestor still running, less the records of it and of the ended processes between. A child never on record (sudo, a setuid or non-dumpable program) lands whole in its parent. A zombie its parent has not waited for yet, or a process that became unreadable, stays on record, with the records of the processes that ended under it, until it ends.
  - A process under systemd --user, or an orphan, is not seen once it ends. A launcher that ends before its child, in one interval, leaves the child to systemd --user, so the child's count never reaches the launcher's parent, whose own writes then read low by the child's record. A parent that does not wait for its children (it ignores SIGCHLD) takes in nothing of them, so its own writes read low by an ended child's record. The bytes may go to any disk, and only this user's processes can be read.
  - The run names each writer's working directory, whether it is on the disk, and the agent session it runs under. The note names the four fastest of every writer the fill's runs saw, each with all it wrote in them (a pid used again is another writer); each run's event keeps eight.
  - Every rule but Docker scans on that run, whatever its cadence. Root's writers (Docker, a system service) cannot be seen. A disk already above 94% is full, not filling fast: it has a problem note of its own, put once and resolved when it drops below.

What a run leaves:

- **Every deletion, offload and prune** is an event (source `capacity`, kind `capacity-delete`, `capacity-offload` or `capacity-prune`), recorded as it happens: what went, its size (for an item, what went with its deletion: a worktree whose build went before it is the rest of it), the space it freed (a prune's tool's own figure, named as the tool's, with whether it is a lower bound or none), what went out of a pruned cache, since when it was idle, and the rule. An offload's names its restic snapshot and the sessions that made the folder; the model data deleted before it is a deletion of its own, recorded before the offload starts. `momentum evidence events --source capacity` lists them.
- **A run's deletions, offloads and prunes are one decided note** (`capacity:run:MS`, the run's start in ms), put with each one's event in one transaction and dated when the last of them went, so a run stopped midway leaves a note of what it did until then.
  - Its title is the run's effect in one line: what it freed on disk, how many items each rule took, the task folders it offloaded with what of them went to restic, those whose model data alone went, and the prunes (`Freed 12.4 GiB: 5 Rust build outputs, 2 leftover worktrees, 2 task folders (1.5 GiB to restic); pruned Docker (3.1 GiB by Docker's count)`). A task folder whose model data went before its offload is one folder, offloaded. A prune done by a tool has the tool's own figure, named as the tool's and not in what the run freed (`at least` when the tool says so, or when one of its prunes printed no total), or says the tool printed no total (`pruned Docker (Docker printed no total)`); a run whose only act is such a prune names it alone (`Pruned the uv cache (2.1 GiB by uv's count)`). A title too long for a line names the prunes by their tools alone, then names the items shorter (`7 build outputs, 4 worktrees, 2 folders`), then counts the prunes, then ends at the last whole clause that fits, with `and more`. A size above zero and below 1 MiB is `under 1 MiB`.
  - Its detail says, in this order: the largest three items with their sizes, what went out of a pruned cache, and what each freed where that is another size (`~/.cache/wt 4.1 GiB (1.2 GiB freed)`, `pruned ~/.cache/uv 12.0 GiB (3.1 GiB freed)`, a tool's named as the tool's); that each offloaded folder's `NAME.restic.txt` beside it says how to restore it, and that model data is not offloaded; how to keep an item next time, one clause per rule in one sentence; then, when a deletion capacity counted took more than it freed, that a file linked elsewhere frees nothing until its last link goes; that a prune's tool printed no total, and how a removed worktree and what the prunes took come back. It stays within 400 characters, the most the phone's view keeps of a detail. One that would not fit leaves those last sentences out, the last first, then names two items, then says how to keep one in fewer words (only what to set) with three items again, then two, then leaves the model data's sentence out, then names one item, then leaves the pointer's out, and last clips the item: how to keep one stays.
  - A prune that removed nothing (Docker lists no record and totals zero, or uv's own count of the cache is the same before and after) is an event only, and a run that took nothing writes no note.
- **Every item only reported** is an event (`capacity-report`), once per item and dated when it was first reported, and `momentum capacity` lists it with why, `--json` too. Most are left by the rule's own policy (whose the item is, the work it holds, a mount it must not reach past, a pointer it would overwrite, a volume that may hold data) and are no problem: an excluded project's item, one of no known project, a build output git does not ignore, a worktree with uncommitted, unpushed or ignored work, an item that holds a mount point, a task folder beside its pointer, and Docker's volumes. They have no note. A note an older build put for them is resolved by the next run, whichever rules it scans.
- **An item its rule would take, which something outside the rule keeps,** is a problem: the uv cache whose prune processes or a lock hold off (`busy`), a task folder whose offload ran out of its time (`too-big`) or whose model data this user cannot remove (`stuck`), and an item the rule cannot read (`unreadable`: a task folder with a directory it cannot list or search, a worktree or a build git fails on). A reason this build does not know is a problem too. Its rule's problem note for that reason (`capacity:RULE:REASON`) counts and names them. The note is put again when an item new to it appears, or when the rule had resolved it itself and its items are back; a note the owner resolved stays resolved until the evidence changes. A rule that finds none of its items any more resolves it.
  - The uv cache's hold is a problem once it has lasted a day, whatever holds the prune off, one reason after another, a quiet wait among them: from the first scan that holds it off until a scan that runs whole and does not (it prunes, or no prune is due), on a run that can trust its look at the processes: one that cannot may not see the holders. Until then the run lists why the prune waits, with no note, and a note an older build put at once is resolved. A run that cannot trust its look neither ends a hold nor resolves its note. The note is dated from the hold's first scan, and one the owner resolved stays resolved until the hold ends.
- **A rule that could not run** (its scan failed, or its last scan's mark could not be read) has a problem note (`capacity:scan:RULE`) that names its error: it could not run, or it stopped partway when its scan found items before the error. What it did with those is on record as on any run. Its items only reported are not, and it resolves none of its notes: the scan did not reach the rest. The disks whose use cannot be read have one note (`capacity:scan:disk`): no fill or full note can come for them. Each error is an event (`capacity-failed`), once. The next scan without an error resolves the note, and so does a rule no longer configured; a rule the run did not scan leaves it as it is.
- **A failure that comes back is a problem again.** The note of a rule that could not run, and those of a run that held its deletions (`capacity:hold:look`, `capacity:hold:docker`, `capacity:hold:sessions`, `capacity:jobs`), are put when their error or reason is new to them, and again when it comes back after a run without it, whoever resolved the note. A note the owner resolved stays resolved while the same failure lasts. Every capacity problem note that is put again while it stands keeps its time, when the problem began, and takes the latest title and detail.
- **A deletion that failed** is an event (`capacity-failed`) and its rule's problem note for failures, whatever its rule's scan did after it.
- **A fast fill** is an event (`capacity-fill`) at every run that sees it, and the disk's problem note (`capacity:fill:DISK`), high importance, put once per fill. At the first run without it the fill is over and needs no one: its problem note is resolved, and the disk's decided note (`capacity:filled:DISK`), dated at the fill's end, says what happened. Its title names the disk, when the fill began (where the window its first run read the rate over began: the growth that showed the fill is the fill's), its last fast run, and what the disk's use grew by between the two, with its sign: a drop after the last fast run is not the fill's (`/data filled fast from Mar 3 14:10 to 14:35 (+18.2 GiB)`; its last fast run's date when it is another day's than the start's). A store that holds no fast run of the fill, or no sample at its last one, gets the span to the fill's end instead. The note is dated when the fill ended, the first sample after its last run; its detail names the writers the fill's runs saw. The report shows it for 12 hours, as it shows every decided note, and the disk's next fill's end replaces it. A fill ends from the store's record, the first sample after its last run, so a run that dies while it ends one leaves the next run the same end. A problem note an older build kept for a fill that ended goes the same way at the next run. A full disk's note (`capacity:full:DISK`) stands until the disk drops below its full percent, put once per stretch above it, and dated from the stretch's start. The ids name the disk by its path, escaped where an id may not hold a character of it (Report, Notes). No notification: the report is the only channel.
- `evidence rebuild capacity` is refused: the record is observations.

Cadence and cost. The rules scan once an hour (docker once a day, `every_hours`), on a dry run and with `--now`. The judging rules (models, targets, worktrees, scratch) scan first and their deletions and offloads follow at once; the uv and Docker prunes come after, so a prune's minutes never stand between a judgment and its deletion. The targets, worktrees and scratch rules share one walk of the targets and worktrees roots (scratch reads the git directories it finds), which does not follow symlinks (a root that is one, or under one, is walked where it leads), leave a root's filesystem or enter `.git`, `node_modules` or a target directory. A target dir is measured only after a look at its directories' times finds no recent build. Each run records how long its process sample took and prints it. Runs that record take turns on a lock beside the store (`momentum.db.capacity-lock`), waiting up to 5 minutes for the one before; a dry run takes none.

`momentum capacity [--dry-run] [--now] [--rule R,R] [--json] [--all]` prints the sampler, each disk and each rule's findings. `--dry-run` deletes and records nothing, runs every rule, reads the store as it is (a store it cannot read reads as no history), and says what deleting each item a judging rule would delete would free. `--all` lists what is kept and pending too. A rule that could not run (its scan failed, or its last scan's mark could not be read) exits 3; the others still ran. A run that records also puts its problem note (What a run leaves).

- **Prior art.**
  - systemd-tmpfiles ages files by their access, modification and status-change times and skips a tree whose directory another process holds a BSD lock on. Capacity follows the lock and the status change; it cannot use access times on a noatime mount, so it samples use instead.
  - Hugging Face's `hf cache ls` dates a repository's last access by its files' access times, which a noatime mount never updates. `hf cache rm` and `hf cache prune` handle the shared Xet store by its `.refs` manifests under each file's lock, which capacity follows.
  - `cargo clean` deletes a whole target; cargo-sweep and cargo-target-gc delete artifacts by age inside one project and refuse while Cargo runs in it. Cargo's own `-Zgc` collects only `$CARGO_HOME`. Capacity works across every project on the machine, judges ownership first, and keeps what Cargo does not make.
  - fanotify would see every open, but marking a mount or a filesystem needs `CAP_SYS_ADMIN`; unprivileged it marks single inodes. inotify watches one directory at a time and does not report reads of a mapped file. Sampling `/proc` needs no privilege and no daemon, and sees what is open or mapped at the run.
  - The Cache Directory Tagging Specification (bford.info/cachedir) marks a directory of regenerable data with a `CACHEDIR.TAG`; tar and restic's `--exclude-caches` skip it. Capacity takes a tagged folder as a tool's cache. systemd-tmpfiles ages a user's cache per directory by the newest of its times (`user-tmpfiles.d`), and the XDG list's discussion of cleaning `$XDG_CACHE_HOME` (2020) found no way to tell whose a folder is or when it was read. kondo, dev-sweep and yeet delete known build artifacts by age. None tells an agent's folder from a tool's or archives what it removes; capacity reads who made a folder from its own record of the agents' commands, and offloads to restic what is not model data.
  - uv holds a shared lock on its cache for the life of every uv process, and `uv cache prune` without `--force` waits for it: uv's documentation says it blocks cache-modifying operations while other uv commands run, allows `--force` only when no other uv process reads or writes the cache, and says a prune removes all centralized project environments, recreated as needed. The source of the prune (0.12 and 0.13) removes every cached environment and every temporary build environment, and takes no lock of an environment of its own; it keeps an archive only when a link of the wheels' or the built wheels' buckets leads to it, so a cached environment, which only `environments-v2` links to, goes with them. `uv cache clean <package>` removes a package's entries in the buckets of its own uv version and the archives only they led to, the built wheels among them, and takes the same lock. astral-sh/uv#11694 reported a prune that deleted a running uvx's environment; astral-sh/uv#16008 asks for a prune by link count; the open astral-sh/uv#20116 (not in 0.13.6) would have `uv run` and `uvx` take a lock on each entry they run from and let uv's prune keep those and what they link to. Until uv does, capacity keeps what the processes it sees use, and follows uv's lock. `docker builder prune --filter until=` is Docker's own pruning. Capacity decides when, and, around running environments, which of uv's entries go.
  - GNU du counts a file with several links once per run. ncdu's unique size of a directory is the files whose every link is in it, and it assumes link counts do not change during its scan. `btrfs filesystem du` reads each file's extents (FIEMAP) and gives what is exclusive and what is shared. uv's cache cleanup counts a removed file's blocks when that removes its last link (astral-sh/uv#21261, since 0.12.6; before, every removed file's size), and its `cache-physical-space` preview (0.12.2) reads extents too, for clones and snapshots (astral-sh/uv#20925). Capacity counts by links as du and ncdu do, before and after each deletion, and reads no extents: on a filesystem that clones (btrfs, XFS), a block a clone shares counts as freed.

## Evidence it keeps

Phase 0 showed that each family needs history the machine does not keep today. The collectors are cheap and keep running when the rest of the tool is down.

- **Sessions:** live state per session and its phase history (how long each session waited on its owner, and on what), input kinds and wait times for owner turns, and the agent's last words before a stop.
- **Machine:** free space per disk every 5 minutes, with the writers behind a fast drop (per-process writes, working directory, the session that owns the process): `momentum capacity` keeps them (Capacity). Per-unit CPU, memory, IO and restart history beyond the journal's retention, plus restart rates with exit reasons. Journal volume per source.
- **Scratch:** an owner and a status for every scratch folder and worktree (which session made it, whether its task or PR is closed, whether its work is pushed). A record of what each cleanup freed, measured, and why: capacity's events hold it for what capacity deletes and offloads, and the sessions that made each task folder it offloads.
- **Money:** per-run model spend of every background job, including the ones that do not report a price today.
- **Memory delivery:** a log of every fact a hook injected (trigger, route, score, matched terms, store revision). A standing labelled set of deliveries graded useful, weak or noise. A miss probe that replays sampled prompts at their historical store revision. Without these, nobody can measure whether a pushed fact helped. In Phase 0 most injected lines were unrelated to the prompt they were attached to, and about half of the facts that applied were not delivered.
- **Latent loops:** jobs that fail and retry on a schedule, tunnels and apps that keep dialing targets that are gone, and timers whose project or script no longer exists.

## Cases

`momentum case` keeps the cases, in kept tables of the store (Store). A case is one answer in progress to one of the standing questions. It holds its family, evidence references, the suspected mechanism, alternatives, the next discriminating test, the expected benefit, the cost spent so far (the model's money and tokens, the time, the runs), its signatures, its status, and a log of every change with who made it (`MOMENTUM_ACTOR` for host commands, `loop:ID` for runner changes), one line for each change or observation.

- **Signatures.** A case is found by its signatures. A detector's names a symptom, a deterministic key of what it saw (Detectors). A finding whose signature no case holds opens a case; one a case holds gives that case the evidence it lacks, and the case keeps its own title. The same evidence twice changes nothing.
- **Cases dedupe by root cause, not by symptom.** A host case command names a root signature (`root:` and a key). Investigation reports add no root signature; validation belongs to a later build. A case that names a root another case holds goes into that case: its evidence, signatures and cost move there (it keeps no cost, so a sum over cases counts each run once), and so does what its investigation found (mechanism, alternatives, next test, benefit) where that case has none. It closes as a duplicate that points there (every case that went into it before points there too, one hop away), and what its symptom brings later lands there too. Any signature merges so, a symptom's as well as a root's. A root links symptoms and never opens a case: a stated cause is a guess until a test tells it from the alternatives, so only a symptom's signature opens one.
  - A case goes into a closed one only when its closer names it (`case close --reason duplicate --into`), never by a signature: the closed case comes back first (`case reopen`, with evidence it does not hold), then takes the other in.
  - A duplicate's own id closes and reopens nothing: the case it went into holds its evidence. Evidence, a change, a signature or a cost given by its id go to that case.
- **Evidence** is a reference: an event (`ev:ID`), a note (`note:ID`), a commit (`git:OWNER/REPO@SHA`), a file (`file:PATH`, absolute or under `~/`, with an optional `@OFFSET`), or an http or https address; anything else is refused. An event's reference always takes the event's own time, kind and summary, and a note's the note's, whatever the caller gives; either must be in the store. Evidence is of what happened: none is dated after now. The material stays where the reference points.
- **Status** runs open, investigating, testing, deployed, measuring, then closed with a reason: improved (with the measurement), not worth it, insufficient evidence, already solved, or duplicate (of the case it went into).
  - An investigation moves a case among open, investigating and testing. A case is in testing only with a mechanism and a fix (its next test) on record: a change that would leave a testing case without either is refused.
  - Only the ship tool deploys a case with its package, and its rollback takes a deployed case back. Only the measure step starts measurement once the change is in effect and closes it as improved with its measured effect.
  - A case closes by hand from open, investigating or testing, with a reason and why, never as improved.
- **A dismissed case does not come back unless its evidence changes.** Evidence dated before the close changes nothing.
  - A case closed as already solved comes back on any evidence after the close.
  - One closed as improved comes back once the fixed-window watch finds its problem back at its old share (Measurement), by its signal in its activity units.
  - Either comes back regressed (its log says so), the same case with its history: its fix did not hold.
  - One closed as not worth it or as insufficient evidence keeps what comes after the close, and comes back once that reaches what it held when it closed: the problem has happened as often again.
  - `case reopen` brings one back by hand, only with evidence it does not hold and a why; one closed as improved or already solved comes back regressed there too.
- **A case unseen past its evidence retention closes by itself**: one open, investigating or testing that has had no evidence for 30 days (about as long as Claude Code keeps a transcript), and has been open for 30 days since it opened or last came back, closes as insufficient evidence on the loop's next run. The problem stopped, which judges nothing about its evidence, so any evidence after the close brings it back. A case opened or brought back on older evidence has its 30 days from then. A deployed or measuring case is its measurement's.
- A loop that fails the same way twice stops and opens a case instead of retrying.
- **Prior art.**
  - Sentry groups events into an issue by a fingerprint, a versioned algorithm that applies to new events only; its similarity grouping merges new hashes into an issue and never splits one. A resolved issue that sees a new event regresses, in the same issue with its history, and "resolve in release" counts only the releases that hold the fix ([Issue grouping](https://docs.sentry.io/concepts/data-management/event-grouping/), [Issue status](https://docs.sentry.io/product/issues/states-triage/)). momentum follows it: a symptom's signature opens a case, a root cause merges cases, and a recurrence reopens the same case. A case closed as improved comes back at its old rate rather than on one event, since a family's signal is a rate and a fix may cut most of a problem, not all of it.
  - PagerDuty folds alerts with one `dedup_key` into the open alert, and opens a new alert for that key after a resolve ([Sending an alert event](https://docs.pagerduty.com/developer/send-alert-event)). momentum does not: a new case would lose the history.
  - ITIL 4's problem management keeps a problem, the cause of one or more incidents, apart from the incidents, finds problems by trend analysis and duplicate checks, and closes one only when its risk is removed or accepted, or it no longer applies. A case is the problem and its evidence the incidents.
  - On Who&When ([Zhang et al., ICML 2025](https://proceedings.mlr.press/v267/zhang25cq.html)) the best automated method names the agent responsible for a failure 53.5% of the time and the decisive step 14.2%. So a stated root cause links cases but opens none, and a case moves to testing only with a test that discriminates its mechanism.

## Detectors

`momentum case detect` runs the families' detectors and files what they find: a new case for a signature no case holds, the evidence for the case that holds it (Cases). Then, when the window is the default week or longer, the cases unseen past their retention close, of the families whose detector read the whole window: a family whose detector failed or did not run, or a shorter window, was not looked at, and the cases of a family with no detector (component health, which the loop files) are not swept here. No model takes part: the failures and owner-burden detectors read the store alone, and two runs over the same store find the same; the sessions detector also reads what the replay of supervision reads (the transcripts' records, Hermes's database). Each reads a window, a week by default (`--since`), and keeps what recurs in it, with at most 200 of each finding's newest events a run. A detector that fails partway files what it found, and a finding the case store refuses is named while the next one is filed: the run's error counts the detectors that failed and the findings refused apart, and `--json` gives a refused finding its `error`. `--dry` files nothing and opens the store read-only, so it migrates nothing; `--family` runs the families it names.

- **Signatures** name their family and its detector's version (`failures/v2:...`; owner-burden and sessions remain v1). A detector that keys a problem otherwise takes its family a new version: its signatures are new, the cases of the old version keep theirs, and another family's stay. A signature fits the case store's 300 bytes: a key too long keeps its start and a short hash of the whole.
- **Failures** (`failures`): the tool and infrastructure failures that recur, three times in two sessions in the window. One session that hits a wall repeats it; a second one says the wall is the setup's.
  - Every transcript result is checked in pages, including older kept results without an error flag. Claude Code and pi require their native error flag. Content tools such as Read, Grep, Glob and WebFetch require native failure status for every harness; their data never supplies a missing flag. `internal/toolresult` names each harness's shell tools in one table: Codex's exec/exec_command/local_shell/write_stdin and Hermes's terminal/execute_code infer a nonzero JSON/header exit (a header is the text's start or what precedes its Output marker, never a command's own words), status error/failed, error payload, false success/ok, or an explicit wrapper refusal/timeout/error. Codex's apply_patch also admits its explicit refusal text. Claude Code's Bash/bash_output/PowerShell and pi's bash use native flags, and so do OpenCode's bash (its exit code and status), Grok's run_terminal_command/bash (its status and envelope) and Kimi's Bash (its error flag): their output text is never read for one. Arbitrary JSON file content is not read as a native result wrapper. A word such as "permission denied" in ordinary successful output is not proof of failure. JSON output/stdout/stderr is decoded before keying. A zero exit and the owner's rejection/cancellation are excluded. No diagnostic surviving the stored cut means no invented key; a retained transcript can repair it on reread.
  - A tool's failed result in the transcripts, for every harness, as the store keeps it: on one line, with the call it answers (the store keeps a call's first 240 bytes). A hook that blocked a call is keyed by the hook and its first words: by the name its message opens with (a dashed word, or a word and guard or gate), or the command Claude Code puts in brackets, else as a hook. A guard's refusal is keyed so too: a guard or gate that names itself, a hook's deny in Claude Code's tool_use_error that opens with a name in lower case (its own messages there open with a capital), and a hold that names who held it. The harness's own refusal (a worktree's isolation, a permission rule or mode, its classifier, a safety check, a block) is keyed by the harness and its kind, not the command it quotes but its programs (but cd beside others); a tool's error (a read, an edit, a write, an MCP server, a Hermes or Codex tool) by the tool. The owner's no (Claude Code's "doesn't want to", his denial with a word of his, the cancel) and a call the harness cancelled because one beside it failed are no failures.
  - A failed command of any harness's shell (Claude Code's Bash, pi's bash, Codex's commands, Hermes's terminal and code), once the harness's header is off its output (Claude Code's exit code, Codex's exit code and timings or its chunk), is keyed only by the message that holds its first mark of the setup failing outside a quoted value (a command, option or file that is not there, access refused, a network, a lock or a resource that failed, a usage message: `usage:`, a program and its options). The message is read in the output with what varies taken out but the mark, and a terminal's colours off, so a path or a quoted name is one letter whatever its length. It ends at the mark, with what follows its colon: another mark (Node's code and its message), or one word (zsh's missing command, the host that does not resolve); a usage message ends at the program it names. It starts at the name of a program the call ran, the closest before the mark within 100 characters, since a program's message opens with its name and its later words may end in a colon too (curl's "after 0 ms: "), though an exception's name after it opens a message of its own; else at the name closest before the mark ("connect: ", "FileNotFoundError: "); else at the mark itself; never before a sentence's end. The key holds no program of its own: a word of the output alone does not say it named one. A command whose output shows the work failing (a test of Go, pytest, unittest, cargo, Jest, mocha or node, by its summary or, since the store keeps an error's first 1,000 bytes, its early banners; a panic, a lint, a compiler's error) is the work's, whatever else it printed; a crash is neither's, so it keys nothing. A Hermes result whose exit code the store's cut left out is read as failed, since the store flagged it so.
  - The mistakes log, Claude Code's own record. A row of the same session and tool as a failed result of the transcript's within 5 seconds is that result, whatever text each kept of it, and counts once; its own rows (a deny or a hold, a model's refusal, a turn's error) count.
  - The incidents an incident detector reports, by their sightings (Session history, incidents): keyed by their text, counted by their repeats since the sighting before, ten in the window, since that detector counts every line a log writes and a network that drops for a minute repeats a few times on its own. A first sighting of an incident first seen before the window counts once, since its count holds repeats no sighting dates. An incident closed or resolved now, as its own event says, counts for nothing.
  - What varies between two sightings is taken out of the key: quoted values (ASCII, GNU's `` `x' `` and curly quotes; a single quote opens one only after no letter or digit: a word's apostrophe is no quote), addresses (a URL, user@host), paths, relative ones too (`.venv/...` as well), a file's name by its ending, ids (hex, a UUID, a long word of letters and digits) and numbers become a capital letter each (Q, U, P, H, N) in the lower-cased text, cut at a word within 80 characters.
- **Owner burden** (`owner-burden`): the owner's own turns that push back, hand a decision back, say a result does not hold, nudge, or repeat, read with the agent's last words since his turn before (within 6 hours): three of one kind in two sessions. Words he answered once are not read again.
  - It reads all harnesses' attributed main-thread owner turns. Native adapters supply provenance where their format records it; unknown or generated input never becomes an owner turn to fill a coverage gap.
  - Only his words count: owner events of the transcripts, by tacit's attribution, in a session's own thread. momentum's own messages are not among them: the transcripts source keeps them as harness text, so a turn of his that opens with the marker holds his words after it and is his (Supervision). On top of tacit's rules, a turn is a program's when it opens with a prefix the machine's configuration names (its wake loops', its briefs': `{"detect": {"program_prefixes": [...]}}`), when it lands in two sessions within 2 seconds, or when a text of eight words or more comes in three sessions of the window (a template). A short text he types every day, a nudge, is his. A turn the transcript holds twice within 2 minutes counts once. A brief that opens a session has no agent's words before it, so it is never classed. A configuration that cannot be read stops the run: without its prefixes, the wake loops' turns would count as his.
  - The kinds, tried in order: attribution (the agent credited him with words or a rule, and he pushed back); handback (its last words handed him a step or a decision, and he pushed back or handed it back); done-claim (its last words claimed a result, and he says it does not hold); stopped (its last words said it waits or will report, and he had to nudge); repeat (he says again what he said in the session within a day, by the words the two share). A push back with none of these before it is not keyed: his words alone do not say what made him step in.
  - The marks are plain English phrasing of a push back, a nudge, a hand-back and a claim, in the code. Their precision was checked on a month of his turns labelled in Phase 0; the labels and the counts stay on the machine.
- **Sessions** (`sessions`): what keeps sessions from moving on without him.
  - Transcript nudges can be read for every attributed harness. Waits and delivery outcomes require observed sessions/supervise events; a transcript alone does not supply a live wait or prove delivery. OpenCode's live scanner reads both legacy and V2 rows with read-only projections, preferring the migrated session.
  - gave-up: supervision used up a rule's tries, or a message of its own did not land (its `case` events, Supervision), by the rule and the reason: a finding at once.
  - outcome: a message that did not land, or whose turn stopped the same way again, three in two sessions.
  - nudged: the owner nudged a stopped session ("continue", "go on", a lone ".") that no rule would have acted on first, keyed by why none would, as the replay reads the stop (Supervision, Replay): its phase, and what kept each rule off. A nudge a program typed (the owner-burden rules) is not his.
  - waited: a session waited on him past the owner window (15 minutes), by what it asked, from the sessions events that saw each wait end. An automated run's waits are not his. Nor is a stop a supervise rule held and resolved on its first try: a wait that lies within the stop of an act of try 1 (it began no earlier than five minutes before the act's `stop_at` and before the message, and ended no later than five minutes after the message), whose outcome says the turn it opened worked, is no case (an access wait held until a usage limit's stated reset, then resumed, shows in the phase scan as hours in needs_you). A later try, or an outcome that failed or went nowhere, still counts.
  - Each part's findings stand when another part fails, and its error comes back beside them.
- **Prior art.** Sentry keys an issue by the stack frames of the project's own code, else the exception's type and value, else the message with its parameters taken out, and versions the algorithm ([Issue grouping](https://docs.sentry.io/concepts/data-management/event-grouping/)). The failure key follows the message rule, since a guard's or a tool's words are its message. OpenAI's harness engineering treats an agent's repeated struggle as the sign of a missing tool, guardrail or document ([Lopopolo, "Harness engineering: leveraging Codex in an agent-first world"](https://openai.com/index/harness-engineering/), 2026-02-11), which is what the failures and owner-burden detectors look for. Phase 0 classified the owner's turns with a model; the detectors stay deterministic, and the investigation reads what they found.

## The loop

The loop investigates, builds a package, reviews it and lands it when live. A case closed as improved publishes its lesson through the host, explicitly marked as unverified. The measure step uses the package's signal, activity units and independent baseline once its change is in effect.

Prior art comes before a new component, workflow or architecture. An investigation weighs a deterministic fix, a tool or interface change, and an architecture change before recommending another instruction.

### A run's inputs

The host prepares the inputs before a run. Host paths are caller arguments. The run has a read-only evidence binary at `/opt/momentum/momentum-ro` on its PATH. It reads a store at `/ro/store.sqlite`, records and unit logs at `/ro/records`, a configuration copy at `/ro/config`, a scrubbed snapshot of tacit's facts at `/ro/clone`, scrubbed snapshots of the repositories at `/ro/repos/NAME`, their history as text at `/ro/history` and the case's diffs at `/ro/diffs`. Preparation runs no model. Its relative times (`--since 3d`) count back from the newest event of the copy it reads, not from the machine's clock, so a copy cut as of a past end answers the window it is asked. Where the executable's own path cannot be read (no `/proc`), the binary refuses every command.

Every copy fails closed on scrubbing. The scrubber must first mask a canary containing the AWS documentation example access key id and a fake password assignment. Texts go through records mode in batches of at most 8 MiB. A record separator in a text becomes a space. A changed record count, missing scrubber or failed scrubber publishes no copy. Names and manifest text are scrubbed too; a path needing masking is withheld. A run gets no Git object database. What the scrubber changes in a repository file, a log entry or a diff is masked, never a reason to leave the repository out; only a scrubber that does not run does that.

The store holds events and notes from the last 30 days of the live store. It holds no case, run, package or derived table. Incident and radar rows rewritten in place remain. Every text column is scrubbed, in pages of rows of which up to four are with the scrubber at once, each written back in the order read. Invalid scrubbed event meta becomes `{}`. `VACUUM INTO` produces one read-only SQLite file in DELETE journal mode, with no WAL.

Records use the host's `momentum evidence show --bytes N ID` and `momentum evidence unit NAME --lines N --bytes N` (the unit's state and the end of its log, clipped to its last bytes at a line start), with one scrubber batch for all headers and full records in a show invocation, and one for a unit invocation. A child is one scrubber start, so consecutive events share one: the records pass asks a child for up to ten with `--separate` (each event as its own child prints it, separated by the record separator, and an event that cannot be shown as an empty one) and runs up to four children at once. It asks only for as many records as could still be written. A shared child that fails, prints more than its bound or returns another number of events is run again one event per child, so each record is kept or withheld exactly as its own child would decide. Records are scrubbed whole before clipping. The records pass publishes that already-scrubbed child output without a second scrub. Evidence IDs keep priority. Neighbours come from exactly the same session, at most five on each side within ten minutes. The shared directory holds at most 200 records, 16 KiB per record (the child's header and marker may add 4 KiB) and 8 MiB including its index. The record count and the total bytes stop collection and the manifest says why; one record over its own bound is withheld alone, and collection goes on. Withheld records and skipped records have separate counts. The store copy scrubs every row's id too, and a row whose id the scrubber would change is left out of the copy. Unit discovery takes at most 25 unique names (the case's own and the journals of the machine's active services, named in A run's inputs) of the form `[A-Za-z0-9@._-]+\.(service|timer)`. The index names each file and its event and time, or its unit, and each withheld record the same way under the name `withheld`, while the byte bound allows its line.

The configuration is the agent system's own, for every harness the machine runs, not Claude Code's alone. It comes only from these roots, each by an explicit allowlist where the harness's directory also holds sessions, logs, databases and credentials: Claude Code (`.claude/mods`, `.claude/hooks`, `.claude/settings.json`); Codex (`.codex/config.toml`, the per-profile `.codex/*.config.toml`, `AGENTS.md`, `hooks.json`, `rules`, `skills`, `agents`); Hermes (`.hermes/config.yaml`, `profile.yaml`, `SOUL.md`, `skills`, `scripts`, `plugins`, `hooks`, `cron/jobs.json`); pi (`.pi/agent/settings.json`, `AGENTS.md`, `extensions`); opencode (`.config/opencode`'s `opencode.json`, `cli.json`, `service.json`, `package.json`, `plugins`); grok (`.grok/config.toml`, `AGENTS.md`, `sandbox.toml`, `hooks-paths`, `hooks`, `skills`); the files agent-sync writes for all of them (`.config/agents`: its `*.md`, `*.txt` and `procedures`); the units that run them (`.config/systemd/user`); momentum's own (`.config/momentum`); and direct shell, Python or Node scripts in `.local/bin`, which are also the launchers of kimi and the rest (kimi has no configuration directory on this machine). Directories named `node_modules`, `dist`, `build`, `out`, `target`, `.next`, `__pycache__` or `.git` are left out of every root. No link is followed. A file must be regular, at most 256 KiB, valid UTF-8 and without NUL in its first 8 KiB. A denylist of names applies on top of the allowlist, case-insensitively: names containing `credential`, `secret`, `token`, `passwd`, `oauth`, `apikey`, `api_key`, `api-key`, `google_`, `vault`, `pairing`, `keyring`, `.pem`, `.key`, `id_rsa`, `.env`, `.sqlite`, `.db`, `.jsonl` or `.log`, and names that are or begin with `auth`. The copy admits no other home root, including `.claude.json`, `.fireworks`, `.ssh`, `.aws`, `.pi/agent/models.json` (it can hold provider keys), any harness's sessions, history, memories or logs, or the broker's environment file. Roots follow the order above and paths are sorted within each root. The 8 MiB cap includes `MANIFEST.txt`; the roots share the byte cap (each gets its demand, or an equal share of what is left, smallest demand first, and a fixed room is kept for the manifest), and the manifest lists at most 500 skipped paths and counts the rest by reason. Files have mode 0444, directories 0555. The manifest lists every file and is summarised in the run's record. This pass copies live configuration. It sets no evaluation clock.

A repository is a snapshot. The host resolves the source's default branch to one commit, lists its tracked files from Git's object store (`ls-tree`, with the host Git environment and execution pins) and reads their blobs with `cat-file`, so no checkout, filter, hook or attribute runs. It keeps the regular files that are valid UTF-8 text without NUL or the record separator, at most 1 MiB each and 256 MiB in all, and counts the rest as left out by reason (binary, large, link, path, total). Links and submodules are never followed. A path the scrubber would change, or one that could leave the tree, is left out. Every kept file goes through the scrubber, in chunks of about 4 MiB (a chunk ends with the file that reaches it, always under the 8 MiB scrub batch), and is written read-only (mode 0444) with what the scrubber returned; the manifest counts the files it changed. The snapshot has no `.git`, no remote, no hooks and no reflog. A link, non-work-tree source or source inside the caller's loop storage is refused. Duplicate sources are read once. Colliding basenames get a short path hash. The refusal of one source (missing, no work tree, no default branch) is a result: the runner counts it in the run's manifest summary and the others and the investigation go on. Only a scrubber that does not run stops the pass.

History comes as text. Per repository `/ro/history/repos/NAME.log` holds the commits of the last 30 days, at most 500, newest first: abbreviated hash, date, author, subject, the number of files changed and, per file, the lines added and removed (at most 100 files per commit). Per run `/ro/diffs/NAME/` holds the patches of at most 30 recent commits that touched a path the case's texts name (its title, mechanism, next test, evidence summaries and log): an absolute path under the repository, a path that ends a tracked file's path, or a file name of at least four characters with a dot that exactly one tracked file has, at most 25 paths. A patch is read without external diff or textconv and scrubbed whole (one over 4 MiB is left out with a note), then cut at 128 KiB; all of a run's patches stay within 2 MiB. Log entries and patches are scrubbed one by one and written read-only. Tacit's store is the same snapshot at `/ro/clone`, with `/ro/history/facts.log` for its log. A tacit snapshot that cannot be made (not a git work tree, no default branch) is left out and the summary says why (`tacit absent: REASON`), unless the cause is the scrubber, which stops the pass.

The runner writes `manifest.json` in the run's host-only directory. It records the store window and counts (rows the scrubber saw, rows served from the scrub cache, rows masked), canary result, records and their bounds, configuration files and skips, leaks, and for each repository and for tacit the commit, files and bytes written, files masked, files left out by reason, log commits and its refusal or reason. It records the run's diffs (paths followed, commits, bytes, entries masked). Counts only: no masked text and no file name that the scrubber changed. The manifest also records the read-only binary's fixed destination and SHA-256. The run's record keeps the manifest's one-line summary.

Prior art: SQLite's [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html) creates a compact database copy. Go's [root-confined file APIs](https://go.dev/blog/osroot) bound file reads. Git's [clone](https://git-scm.com/docs/git-clone) and [cat-file](https://git-scm.com/docs/git-cat-file) interfaces provide independent clones and a stream of their objects.

The pass-level store, configuration, tacit snapshot, repository snapshots and logs are prepared lazily when the first investigation, build or review is about to start. The store copy, the configuration copy and the snapshots read different sources into different directories and are made at the same time, so the pass waits for the longest, not for their sum; the first that fails stops the others and its error is the pass's. The pass logs how long each took. They are shared read-only by the pass's runs and removed when the pass ends. A dry pass prepares nothing. Records and `case.json` are prepared per run. A missing scrubber, failed canary or failed copy of the store, the configuration or the records skips the step before reservation. No model starts and no run is charged to the case.

A live pass keeps a persistent scrub cache so it scrubs only new or changed rows and files instead of a month of events. It is one SQLite file, `scrub-cache.sqlite` in the data home, mode 0600, on the host only: it lies outside the loop storage (a path inside it is refused) and no run binds it. An entry is keyed by the SHA-256 of the scrubber's identity (its arguments and its program's bytes), the kind of text and the exact texts of one unit (a row's id and columns, a file, a log entry, a patch), and holds what the scrubber returned for them. A different scrubber or different text finds nothing. The canary check runs before any use, so the cache never stands in for it. A pass told to stop does not count as a cache failure. Its entries and the day each was last used are separate tables, so a daily touch rewrites small rows and a prune reads an index. Entries that no pass used for 7 days are dropped when the pass ends. A cache that cannot be opened or fails is dropped (the file is removed) and the pass scrubs without it, with the manifest saying so; it can slow a pass down but never changes what is published or stops it. The store manifest counts rows scrubbed and rows served from the cache, its own rows only, while the other copies use the cache at the same time. The evaluation keeps its as-of clones and its own master copy and uses no cache.

`momentum-ro` provides `evidence events`, `evidence show ID [ID...] [--bytes N]` (up to ten), `evidence status [--since DUR]`, `evidence unit NAME`, and `case show [--json]`. Events use the host's filters, time syntax, ordering and limit rules. Show prints the event and its frozen record, or says it is not among the run's records; it also lists indexed records from the same session. Unit reads its frozen file, never systemd. A record that is a link, even one inside the records directory, or not a regular file is refused, and a read stops at its bound. Case prints the same compact text as the host, with the newest 20 evidence references and last 20 log entries; JSON prints the input file. Formatting and event queries are shared with the host. Records are already scrubbed and are not scrubbed again. Defaults are `/ro/store.sqlite`, `/ro/records` and `/run/input/case.json`; `--store`, `--records` and `--case` override them for tests only. Python3's sqlite3 still works.

The mode is selected only by the basename returned by `os.Executable()`, never `os.Args[0]`. A binary named `momentum-ro` reaches only these readers. All other commands exit 2 with "momentum-ro reads the run's copies and changes nothing". It opens SQLite with `mode=ro&immutable=1`, without host schema checks, migrations or sidecars. It reads no configuration, opens no store for writing, uses no network, runs no other program and dumps no environment. This is no door: its store and records are the run's own copies. A copy renamed `momentum` uses the host parser again. The sandbox still exposes no host store, host configuration or host network to reach. The run reader cannot write its inputs.

Prior art for this reader: SQLite's [URI filenames](https://sqlite.org/uri.html) define read-only immutable connections; Go's [os.Executable](https://pkg.go.dev/os#Executable) identifies the running executable independently of its arguments. Sources checked 2026-11-03.

The store's `events` columns are `id` (24 hex characters, referenced as `ev:ID`), `source`, `source_key`, `ts` (milliseconds since the epoch), `session`, `agent`, `harness`, `model`, `cwd`, `actor` (owner, agent, tool, harness, detector, unknown), `kind`, `tool`, `summary`, `meta`, `ref`, `heuristic`, `experiment` and `ingested`. `notes` holds `id`, `kind`, `title`, `detail`, `effect`, `links`, `source`, `importance`, `at` and `done`. The owner's words are only his own turns, with actor owner. Python3, git, jq, rg, grep, sed and awk are in `/usr`.

### The runner

`momentum loop` runs one pass. A second pass fails at once on `momentum.db.loop-lock`. A live pass checks `sandbox.Available(true)` once, removes the input directories a killed pass left, and stops leftover `momentum-run-loop-` units before any investigation starts. A SIGINT or SIGTERM ends the command's context: the pass stops its runs' units (their sandboxes die with them), records each run as stopped, removes its inputs, and starts no other run. It then:

1. Ends stale running rows after the allowed run time. Their original reservations are charged once. The host's authenticated saved report, or a killed investigation's findings file, is recorded first.
2. Runs the detectors and sweep (Detectors).
3. Measures deployed, measuring and improved cases without a model (Measurement).
4. Selects one case per family: testing first, then investigating, then open, by evidence count. One case builds in a pass. Running reservations, case budgets and the stop rule hold selection. Shared inputs are prepared once. Host preparation gates the repository and makes both clones before the build starts. Each run is reserved before it starts. An unreadable package, failed deployment or refused resumed rollback skips that case with its reason. Other cases and families, reviews, landings and lessons still run. An unreadable package gets one low passive note. Store read failures still end selection after joining reserved runs.
5. Records investigation findings and build results with relay-observed accounting. Each host build stage has its own failure key: preparation, inputs, toolchains, run, report, package, authority, patch, check and proposal. Host preparation failures such as clone, fetch or input-file errors complete a zero-model-cost build step and count for the stop rule. Repository-gate and busy refusals, scope holds and a held ship lock skip the case for this pass, with the reason and one low passive note per cleaned cause. Preparation writes no run. The same holds in build check and proposal, including a proposal waiting for its measurement readers, remove the reservation and store no run or run count. Model work already done keeps a separate charge receipt in the case log and still counts toward spend budgets. An unchanged hold stays resolved if its reader resolved the note.
6. Reviews proposed changes in clean contexts. Findings and their counts are kept before posting. A review whose recording meets a held case lock, or a package head that moved since its export, is a hold (`hold`): the stop rule does not count it, and the next pass reviews the current head again. A post failure leaves a pending review for the next pass, without another run or round. The repository gate is checked on every posting attempt. A posted high or medium finding returns the package to build. A posted clean review permits landing only when live. A pass that is not live skips landing without repeating a case note. Other landing refusals are noted once per cause.
7. Keeps a low passive note for a package that used its three rounds or had two proposals closed without merging and still needs work (`loop-rounds:CASE`). A closed, unmerged pull request uses one proposal. After two, the runner reports the case and builds it no more. The owner may still propose its checked package. A review skipped for its case budget or the stop rule leaves one low passive note per cause (`loop-review:CASE:budget` or `loop-review:CASE:stopped`). An unchanged cause stays resolved if its reader resolved the note. A conflict after the third clean review, an unreviewed replacement head, and an exhausted prepared or checked package wait for a person. No fourth review or replacement build starts. A pending clean post needs no new round. Package read errors preserve the note. A resolved note stays resolved while the same change waits; leaving the state resolves it.
8. Publishes the stored build lesson for an improved case. No model run or publish step is reserved.

`momentum loop --dry` selects without writing, recovering runs, building inputs or discovering programs. It opens the store read-only, migrates nothing and creates no SQLite sidecars. An exclusive byte-range lock keeps the immutable view stable. A busy store, nonempty WAL or rollback journal is refused. A missing store is absent; an older schema needs migration by a writing command. An existing pass lock is checked without creating one. `--family` and `--case` narrow measurement, selection, review, landing and lessons. `momentum loop runs` lists runs and live spend in the last day and week. A never-started row uses its end time for listing and is marked never started. It adds no run to its case.

### The investigation

The investigation is the harness's native agent, with the native brief, standing constraints and machine rules. It receives no family skill or case bookkeeping procedure. It keeps findings as it goes in `/out/findings.md`, with Mechanism, Alternatives ruled out, Fix and Summary headings. Its schema report has `mechanism`, `alternatives`, `fix`, `summary` and optional `repo`. `repo` is the NAME under `/ro/repos` where a code fix belongs. The host logs that name with the case episode; no store schema changes. A testing case without a repository waits with a low passive note (`loop-repo:CASE`) and reserves no build.

The reservation keeps the case episode used to prepare the brief. The host records the report only in that episode. A report replaces the mechanism, alternatives and next test. A field with no letter, digit, symbol or punctuation (spaces, joiners, fillers) names nothing. A mechanism and fix move the case to testing. A successful incomplete report closes it as insufficient evidence. New evidence can reopen it in a new episode. A findings file updates only the fields it contains and leaves the case investigating. A case that merged, advanced or reopened while the run ran rejects stale findings.

When a run has no report, the host reads only `/out/findings.md` from the writable directories. It opens that one regular owned file through a confined root, refuses symlinks and pipes, and reads at most 1 MiB from the same descriptor. It scrubs the text before persistence. Everything the run writes is untrusted data. Host programs and Git never run in writable run directories. Patch export runs inside its own sandbox.

The harness binary is resolved and bound read-only at `/opt/claude/claude`. A fixed shell inside the sandbox emits a random per-attempt startup witness on the bounded diagnostic stream, then execs it. A manager or bubblewrap setup failure emits no witness and is recorded as never started. There is no separate status pipe. It runs bare, in print mode, with the named built-in tools, strict MCP configuration, permission prompts disabled and session persistence disabled. The host archive is its transcript. The harness reads the system prompt from `/run/input/system.md` and gets `--add-dir /ro`, the report schema, model, turn cap and spend cap.

The environment contains the relay's Bedrock variables and `CLAUDE_CONFIG_DIR=/home/agent/.claude`, `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`. `ANTHROPIC_BEDROCK_BASE_URL` uses private loopback at `sandbox.RelayPort` (8787) and the relay's path prefix. No inherited environment enters. Checks assert variable names only. Each unit is `momentum-run-loop-` plus the cleaned lowercase run id. A fallback appends `-fallback`. Its relay socket and trusted inputs live in `HostDir(run)`. Streams stay there too: 64 MiB for the transcript and 8 MiB for diagnostics.

### The build

The host maps the investigation's repository name through the pass's admitted `loop.read_dirs` repositories (those the snapshot could read). A build clone keeps history that no scrubber has seen, and the clone holds what its fetch of the remote brought, not only what the source checkout holds. So every build's clone (all its objects, its refs and its generated configuration) is scanned by the scrubber after it is cloned or refreshed and before it is mounted: if the scrubber would change anything, or an object is over 8 MiB, the clone is removed and the case waits as refused, though the repository is still investigated from its masked snapshot. The clone has no reflog. The name never becomes a host path on its own. `Ship.Prepare` checks owners, exclusions, scope and busy work, then makes a host clone and an independent build clone at the immutable BASE. A run gets that clone writable at `/work`, including its `.git`. It may commit freely. The host never inspects those commits, its index or its configuration.

Builds have the shared read-only `/ro` inputs and the same case file as investigations. A revision gets the last review as `/run/input/review.md` and the cumulative host-kept patch as `/run/input/previous.patch`. Before rework on a moved base, the host fetches the new base and replaces the clone; it does not read the old clone. The build fixes one cause with its discriminating test, runs that test inside, then reports `summary`, `test`, `title`, `body`, `rollback`, `signal`, `window` and `lesson`, plus optional `installed` when the machine runs a binary or installed configuration. The window is whole weeks, such as `7d` or `14d`; the signal names source, kinds, match and optional tool and harness. The installed path names a regular file without links in an admitted `loop.read_dirs` directory, outside run storage and writable caches. Only the host reads it. The owner may name any regular installed file with `ship propose --installed FILE`. The lesson is one line of at most 300 characters. The body is at most 64 KiB.

Build and review procedures are short embedded skills. Investigations have the native brief. A change weighs a deterministic fix first and carries its test. It never changes the loop's detectors, measurement, gates, sandbox, skills, budgets or configuration, takes another session's work, works in an external repository, uses paid compute or reaches the owner's phone or desktop. A run has no network for research or repository traffic. If prior art needs a search, the proposal body says that the run could not perform it.

Toolchains and module caches are read-only `sandbox.Bind`s under `/opt/toolchain-N`. Overlapping sources share their outer mount. Toolchain paths and explicit environment settings map into those mounts. `loop.sandbox_read` adds read-only test roots there too. The user's home stays empty. Go's compiler and module cache are available; build caches live in tmpfs `/tmp`. Test environment names are explicit and tests inspect names only.

After a successful report the host starts a second fixed sandbox unit, `momentum-run-loop-patch-ID`. It has no relay or harness. Only `/work` and `/out` are writable. It stages all files and exports a cumulative binary diff against BASE to `/out/change.patch`. Both Git calls pin `core.hooksPath=/dev/null`, disable fsmonitor, attributes, signing, submodule recursion and maintenance, and use a clean environment. Diff disables external diff and text conversion. Run-produced settings cannot select host execution.

### The ship tool

`momentum ship` is the owner's CLI for prepare, check, propose, status, land and rollback. Agent runs return reports; all ship operations belong to the host. Packages live under `loop/packages/CASE`, independent host clones under `loop/host/CASE`, writable build clones under their run's `/work`, and disposable exports under `loop/exports`. Owner preparation also makes a clone under `loop/work/CASE`. Source checkouts and other worktrees keep their history and work.

The host reads `RUN/out/change.patch` once through `os.Root`. It refuses links in any component, pipes, unowned or nonregular files, and a file over 16 MiB. Check and proposal consume that same byte snapshot. Patch paths are clean and relative, with no `.git`, `..`, base symlink or gitlink. Ambiguous diff headers are refused, including an unquoted path with spaces in a subdirectory with spaces. New and changed files use modes 100644 or 100755 only. Binary literals and deltas are bounded before application. Changed blobs are at most 8 MiB each and 32 MiB in total. The result-mode and total-size checks in `checkChangedFiles` are defense in depth behind the patch parser and application bounds. Cleanup directory opens use `O_NOFOLLOW` as defense in depth behind no-follow inspection, including against a racing replacement. A refusal or nonapplying patch changes no remote state. Nothing else in the build's `/work` or `/out` is read by the host.

The host resets its index and files to BASE without moving the proposal branch, applies the bytes with indexed binary patch application and no network, then writes a tree object. Protected paths, both sides of a move, signal edits and test files are checked against this immutable object. Accepted patch bytes remain in the host package for recovery. Host Git disables hooks, fsmonitor, external diff, signing, submodules, attributes, tag following and automatic maintenance. Source configuration names programs only when the gate refuses it; includes are inspected by name without expansion. Host storage links, alternates and worktree pointers into run storage are refused before Git. Every commit uses the owner's global identity. GitHub authentication uses the host's helper.

`Ship.Check` exports BASE with the candidate's test files, then the changed tree. Each test runs through `sandbox.Spec` with no relay or harness, only a writable export at `/work`, toolchains, admitted read roots and tmpfs caches. The capacity gate runs before each test. The command is one allowed test runner and its arguments, without a shell. It must fail on BASE and pass on the candidate. Test copies are root-confined regular blobs with their executable modes preserved. Outputs are bounded and cleaned whole before clipping. The check pins its tree and keeps its original command in a separate host-only input; the package holds cleaned display text.

`Ship.Propose` applies the same cumulative snapshot and requires the checked tree. Its signal hits at least five activity units in a whole-week gate and counts at least half the case's events in that gate. Its baseline is the three independent windows before the gate. A signal whose reader began inside the four windows is refused: the problem is too new to measure with that window. It records every counted source and requires complete reads (Measurement). Removing a line holding signal text is refused, including binary-classified files. The guard also joins adjacent quoted literals and literals joined with + across source lines, using the old file and requiring an edited literal or joining operator. Changing just one fragment is refused too. It does not evaluate arbitrary runtime string construction. It records the measurement plan, rollback and lesson, cleans title and body and makes mentions and references inert. A direct tree commit must equal the checked tree. A revision uses the previous proposal as parent and must change the reviewed tree. Publication leases the exact `PublishedHead`, or an explicitly absent branch, never a refreshed tracking ref. A lost push response is adopted only for the exact candidate. Pull request creation reconciles branch, base and exact head against all existing requests before creating one.

A review reads a plain stable host export of the proposed commit at `/ro/change`, read-only with no `.git`, and the cumulative patch at `/run/input/change.patch`. Its package input holds title, body, rollback, plan and the check result only. Earlier reviews, output tails, execution arguments and host paths stay outside that input. Its schema requires a nonempty summary, findings and reviewed_files naming every changed file once; each finding has severity, where, problem and fix. The host records a review under the case lock, with at most three rounds and one review per head. The reviewer supplies the head it exported. A missing head or a package head that changed since that export refuses the verdict. High and medium findings block landing. A clean review is kept before posting, and an unposted review lands nothing. The host rechecks repository and case authority before posting or changing state. Review posting and the build clone refresh, relocation and package save take the case lock and reload the package inside it.

`Ship.Land` uses only the host clone, when live and cleanly reviewed on its current head. It rebases on the fetched default branch, runs the original recorded test on an export, publishes the exact rebased head with its lease and pushes it to the default branch as a fast-forward. Journals reconcile interrupted publication, landing and deployment receipts. An uncertain publication retains its exact candidate. Once publication is known, a moved default branch can trigger another checked rebase. Proposal-branch deletion leases the published landing head; another writer's moved branch stays. Cleanup intent is journaled with the landing, before deployment or deletion. A refused or interrupted cleanup is retried at the next live case selection. Cleanup refusal is reported alongside the successful landing receipt. Before each default-branch push, the host reads the pull request state and requires OPEN. An already accepted landing is reconciled before this check, since GitHub then marks it merged. A CLOSED, unmerged request clears the landing journal and its reviews, returns the package to checked, increments its used-proposal count and records one note. One automatic retry remains after the first closure. After two closures the runner stops building the case and reports it. The owner can still propose the checked package; a closed request is not adopted by proposal reconciliation. A rebase conflict records `RefreshBase` and permits rework only while a review round remains. After the third round the package waits.

`Ship.RollBack` reverts the landed commits in a host scratch worktree and pushes a journaled candidate as a fast-forward. Rollback pushes skip the public-patch content scan: they restore content already published by the repository. Proposal and landing pushes keep that scan, and every rollback push keeps the repository gates. A resumed rollback requires loop.live. A retry reconciles that exact head and completes receipts once. The case must be deployed or measuring before a revert starts. The passive decided note is written before its case receipt. A kept change is never rolled back by this step. If neither the journaled revert nor the moved default branch is an ancestor of the other, the host recomputes the revert on the fetched default branch under the same gates. It preserves the original reason and replaces the journal only when the new revert is ready. An uncertain ancestry read retains the old journal. When its case regresses, preparation archives the previous host package and creates fresh independent clones. A new preparation reads a leftover proposal branch and leases that exact remote head. It never reads the run clone. `ship status` reads the host package.

An improved case publishes its stored lesson without an agent run. The host applies Public to both its description and body, reserves its cleaned text on the case, and writes to tacit under `momentum-lesson-CASE` with the description prefix `unverified lesson from a loop run: `. Measurement validates the outcome, not the model-written advice. The prefix keeps that advice unverified for readers even though the storage kind is observed. A receipt follows the write. The first reserved text is reused after a partial failure and passes Public again before publication. A reservation without a receipt cools down for one day. The owner may also use `momentum loop lesson --case ID --text TEXT`. The measure step closes a case as improved only after its signal's share falls beyond chance.

### Measurement

`momentum measure` is the measure step, which the runner takes on each of its runs too; deterministic, no model. Every writing measure or watch operation takes the case's ship lock and reloads the package inside it, through its package writes, case decisions, keep and rollback. A held lock skips that case for the pass with no failure or run, and one low passive note per cleaned cause. A dry measure takes no lock. A deployed or improved case whose older plan has no counted time (`At`) or activity units (`Units`) is not measurable by this step: it waits to be measured by hand, with one low passive note and no repeated failure. `--family` and `--case` narrow it as they narrow a run, and `measure --dry` opens the store read-only, takes no lock and changes nothing. `loop --dry` keeps its exclusive immutable store view and creates no sidecars. A proposal defaults to a week; the build step chooses a week, or two for a rarer problem. The plan refuses a window that is not a whole number of weeks: shorter windows compare different days of the week. A fixed-seed simulation with 100 weekday units and 60 weekend units, weekday shares of 4% or 5% and weekend shares of 0% or 1%, pins false keeps below 5% among admitted unchanged plans (about 4%); the change takes effect one to three days after the plan. The other rates this section quotes are exact enumerations of the step's own decisions over every outcome of the windows, recomputed by a test of `internal/measure` that fails when SPEC prints another figure. Its gate counts the last window before the plan, `[At-w, At)`. Its baseline counts the three windows before the gated one, `[At-4w, At-w)`. The plan records both counts, their activity, the signal's source and every source whose events its units can count in those four windows (a sessions' measurement records no source of events without a session: a capacity run, an incident), but one whose first event falls inside them: it began there, adds activity the baseline held in part or not at all, and is left out of both sides, as a stopped one is (the signal's own source cannot be left out, and the plan is refused). A reader is dated by its first event, so one switched off and on again is not caught. The four windows are those before the proposal: a failure inside them moves the boundary back, and the span with it, but a reader old enough at the proposal is not too new for the plan the failure moved (that refusal would come back at every run, and no wait or build could change it). A reader is left out before the boundary is sought, so one that has finished no read holds nothing. Its boundary is the newest moment all those sources have read past, at most now, and before the first incomplete run of one inside the span (Read windows). A store no more than one window behind admits a proposal or revision without waiting for a read started after the proposal. A store further behind refuses it. A waiting proposal takes a new boundary when the readers advance. Its window after starts when the change is in effect.
- **Read windows.** Every decision requires every recorded source to have read past the window's end, even when that source has no event in the window. Later activity uses the recorded sources still live. Every ingest source records the run's start in `SOURCE:read` after a complete read, and so does each source its ingest stores events under (the radar's `radar-feedback`, which answers `SourceLive` as its reader does). A sessions scan reads each harness on its own: it records a harness's read when that harness's scan and the snapshot complete, dated 15 minutes (the stamps' keep) before its time, since a session gone from a scan is written vanished that much later at its last sighting, and the source's own read when every harness's did. Supervision records the same for the harnesses it decided for. A session the scan read in part (a query of its harness's own failed) leaves its harness's run incomplete, in a sessions scan as in supervision: its stamp is left as it was, so a wait that began and ended while it was read short writes no event. A capacity run records a read when it is not dry, reaches its end and has read every configured rule, root and disk. A rule whose scan failed, a models root it could not list or a disk whose use it could not read makes the run incomplete, even when the command returns its other observations without an error. A signal that names a harness is read for that harness: another harness's failing scan neither stops it nor holds it. A cursor's update time is never a read record. **A command's run that read less than it should have** (a scan that failed, a snapshot that lost its harnesses, a session read in part - a scan's or supervision's - a capacity rule, models root or disk it could not read, or a run that stopped on an error) **loses what it should have seen, and no later run puts it there**: a wait that began and ended inside the failure leaves no event. It is recorded as an incomplete run - one record an hour of its harness, or of the source as a whole, which keeps the first and the last run of the hour - and a window reads only through the first incomplete run inside it, however complete the runs after it are. A run that never started leaves no record of its own (a timer stopped, a run that gave up on the lock of a stuck one, a process table that could not be read, the machine off). A complete run of a scan or of supervision that starts more than 15 minutes (the stamps' keep) after the harness's last complete one therefore records the stretch between them as one incomplete run, and a window that holds it is never read, however complete the runs after it are. The stopped rule defers a decision while a source is stopped; it does not cover the stretch, since a source that reads again is live. A capacity run has no harness and no stamps, records no such stretch, and is covered by the stopped rule alone. A source that fails at least once in every window is never read whole, and the window after a change starts again at each failure. A plan whose span holds one has its boundary moved back before it, and waits when that is more than a window ago; the window after a change starts again after the failure (Then); a watched window that holds one breaks the run of windows at the old share. Transcripts, and incidents for a file the process cannot read (the run fails), record instead each partially read run's start and the newest modification time among its failed files, since a later complete run reads those files again: that run covers a window only when every failed file was last modified before the window's start, an unlisted source or a failed file whose modification time is unknown certifies nothing, and a complete read drops the partial runs that began before it. The gate and baseline, both windows after, an interrupted keep's recovery and every watched window have the same read check. An unread window makes no decision and says which source is behind. After a window of waiting, a passive `measure:CASE` problem note names the sources behind, and only them; a successful read clears it. Rebuilding a source drops its read records and per-file records with its cursors, in the same transaction. A rebuild and an ingest, and two ingests, exclude each other with one lock: a run that finds it held fails at once and names the process that holds it. The records are derived (Store): a schema step that reads again drops them, the incomplete runs of that time with them.
- **Stopped sources.** A recorded source switched off (`supervise.off`), no longer configured, or a command's (a sessions scan, supervision, a capacity run) that has not finished a complete read for a whole window, or in more than a window since its first event when it never finished one (one harness's scan that keeps failing, a session read in part on every run, a timer that no longer runs), is left out of both sides; a scan and supervision are read for the harness the signal counts, so the harness it does not count stops nothing of it. The baseline is recounted over the same live sources as the later windows, and the case's note names the source left out. The watch recounts its completed windows when that set changes. When the signal's own source stopped, there is no decision, and a note says so; a proposal refused for it is a wait, recorded with its plan and signal as one refused for a read is, and the build for it is passed over until the source reads again. A waiting proposal's note goes once its case leaves testing. A sessions scan keeps the working directory on each session's stamp, so a vanished loop run carries it and stays out of activity.
- **In effect.** A Go binary with `debug/buildinfo` settings `vcs.revision` and `vcs.modified` is in effect when its revision (a commit name, never anything else) holds the landed commit as an ancestor or equals it, and its tree was not modified or, modified (Go counts an untracked file too), held the change's own files as the revision has them. A build from a modified tree is judged once, at the first run that sees it, and the decision stands while the binary's hash and time do, as for another installed file: the checkout moves on without the binary, and neither a commit nor an edit undone says what it was built from. It is in effect only when the change's files then match the revision and none was modified after the binary; a git error that may pass decides nothing, and the run asks again. A rebuild from a revision without the change is out of effect. For another installed file, the first run that sees the checkout hold the change records the newest modification time among its changed files; with none, the landing dates it. That time stays, including while a deployed case waits for its build. The installed file must be newer. The run that checks it records its modification time, hash and whether it holds the change. An unchanged file keeps that decision through later checkout edits or branch switches. When the file changes again, the checkout is checked again, as it stood when the file was written: the commit its HEAD's reflog names at the file's modification time (HEAD as it stands when the reflog does not reach back), so a rebuild from an older tree stays out of effect though the checkout is back on the change by the next run. That check reads only the commit the reflog names, so a build from uncommitted edits, or from another work tree or clone, is not checked. A rebuild from a checkout without the change stays out of effect until another file change from a checkout that holds it. Without an installed file, each run checks the checkout as it stands. The build names an installed file when the machine runs a binary or configuration built or installed from the repository, and review checks it. In a build report the file lies in a directory of `loop.read_dirs`, which a run cannot write, and not in the build's work tree, which it can: the plan stats it, and the measure step opens and hashes it later, outside the sandbox, so a path elsewhere would tell the run whether a file of the machine's exists, and a path the run could change would not be the one accepted. The step opens the file once, without following a last link and without waiting on a pipe, checks the descriptor (a regular file), hashes that descriptor and reads the build information from it: a path swapped for a link, a pipe or a directory since the proposal is refused, and the plan refuses a link at the proposal, so the file to name is the one a link points to. The owner who installs a tool elsewhere lists its directory in `loop.read_dirs`. For every installed file, a transient git error records no decision about that file, and the next pass checks it again. A git error says why the checkout could not be checked. A resumed landing keeps its recorded time. A change out of effect waits without a decision; after a window out of effect, its `measure:CASE` problem note says so. A new measuring gap is dated from its first run, not the landing; a deployed case's repeated wait keeps its note's time. When it returns, its window after restarts from that run, its deployed time moves, and its log records the restart.
- **Units of activity, not events.** A signal counts in units: the hours of the sessions (of its harness, when it names one) in which they did anything, and of those the hours in which it counts an event; the hours in which the owner spoke, for a signal of his words alone (both later hits and activity keep that actor filter); the machine's hours, for events no session holds (an incident, a capacity run). A problem that repeats inside one hour of a session counts once there. More calls inside that hour move nothing; sessions added or lengthened by a change move session hours, and asking the owner more can move owner hours. A quieter week is no fix. Events whose working directory is the loop's own directory or below it count in no window, as neither hits nor activity; both its raw path and its `filepath.EvalSymlinks` path are excluded. A tool result is a hit only when its metadata says `"is_error":true`; a successful result quoting an error is no hit, and the query leaves it out. A count reads at most a million events of the signal's source, kinds and harness over a span, newest first, and fails when the span holds more rather than count the newest alone.
- **The test** is Fisher's exact test, one-sided: under no change, which of both windows' units hold the problem is chance, so the after window's count of them is hypergeometric, its draws the after window's units. The change helped when that count is lower than chance makes likely (p below 0.05) and its share fell. The test assumes independent units: that which of them hold the problem is a draw, whatever the others hold. The hours of one session are not independent (a session that hits a wall hits it again), so for a problem that clusters in sessions every rate below is a floor, not a bound (Why five). A window after too quiet for even a drop to none to pass (which reads the count before and the activity after, never the count after) waits one more window and then counts both; still too quiet, the change goes back, since nothing could show it helped.
- **Why five.** The gate requires at least five units with hits in the last window before the plan. At equal activity, a drop from five to none has a chance of about 1 in 32 under no change, and one from four about 1 in 16. The gate selects a window that reached five, often by chance. The baseline is the three windows before it, disjoint from the gate, so the gate selects none of the baseline. The plan is refused when even a drop to none over two windows at the gated window's activity could not pass: the problem is too new or too rare to measure with that window, so use a week, or two for a rarer problem, once enough history is read. Exact enumeration at 50, 100 and 200 units per window and unchanged shares of 1% to 12%, including the quiet-window wait, pins false keeps below 5% (at most 3.8% on this grid) among cases that pass the five-unit gate, including those the baseline refuses. Among plans the baseline admits, the false-keep rates are 36.8%, 14.4% and 6.7% at 50 units and shares of 1%, 2% and 3%, and 14.6% at 100 units and a 1% share. Baseline refusal keeps the gate-passing rate low at rare shares; the admitted-plan rate conditions on a rare high baseline instead. The five-hit gate makes admission rare too, keeping the overall chance low. Neither denominator gives a 5% bound among admitted low-count plans. A longer whole-week window supplies more activity for a rare problem. The enumeration pins both denominators. At 100 units per window, the baseline admits about 55.6% of gate-passing cases at a 2% share, 88.8% at 3% and over 99% at 5%; among admitted plans, removal is detected in all cases on this grid, including the wait for a second window. The case's count before is the baseline's, not the gate's. All these rates assume that each unit holds the problem independently of the others. Hits cluster in sessions. Take an unchanged problem at a 5% share and a window of 10 sessions of 10 session hours, a session prone with probability `pi` that holds the problem in each of its hours with probability `h`, so that `pi * h` is 5%. Among admitted plans, the step keeps 2.65% of them with independent hours (`pi` 100%), 5.73% for `pi` 50% and `h` 10%, 12.6% for 25% and 20%, 32.3% for 10% and 50%, and 49.6% for 5% and 100%. A kept change is one whose problem fell by more than independent hours make likely, and a problem that clusters in sessions falls that far by itself far more often: the rates above are floors for it. The unit stays the session's hour; a session as the unit would need longer windows or a lower gate. What the step does to a real partial fix, among admitted plans: at 100 units a week, a 5% problem cut in half is kept 18.4% of the time (cut to a quarter, 45.2%) and a 10% problem cut in half 38.7%; at 300 units a week, a 5% problem cut in half is kept 56.0%. The rest read as no measured effect, and a live loop rolls them back.
- **Drift.** The baseline starts four windows before the plan. A problem drifting down by itself can read as a fix. With a 5% share in the window after, a 3% weekly drift keeps 4.0%, 6.8% and 9.6% of unchanged plans at 100, 300 and 600 units a week; a 5% drift keeps 5.3%, 10.2% and 16.4%. These take the change in effect at the plan; with the one to three days the weekly model assumes, at two days, they are 4.1%, 7.2% and 10.4%, and 5.6%, 11.2% and 18.4%. The stationary false-keep bounds do not cover this drift.
- **Then.** A change that helped closes its case as improved, with its counts and its p (`case show` holds them); its package is kept, and a shipped note names the span measured, including both windows when it waited. A window after that holds an incomplete run of a counted source (Read windows) decides nothing: it starts again after the failure's last run, once the source has read past it (the case waits until then, so the window moves once, not at each run of a failure that goes on), as it does after a gap out of effect, and the case's log says why. A close whose keep was interrupted is finished on the next run; keeping twice is harmless. One with no measured effect is rolled back by the ship tool, only while the loop is live (it says there was no measured effect, not that the change did not help: Why five has how often a change that helped in part is kept): while it is not, the rollback is held, with a decided note, once, that says how to roll it back by hand, and the case keeps measuring. The note names whichever window had no activity; an empty window after is too quiet to tell. A rollback that fails leaves the case measuring with its reason on the case, logged once per cleaned cause, and the next run tries again; the second failure in a row puts a problem note in the report (`measure:CASE`). That note, and a not-in-effect note, goes once the case leaves deployed or measuring, including after a rollback by hand. A revert that went in, or was begun and journaled, while its case did not follow is finished before anything is measured, whoever began it: the case goes back to testing.
- **Back.** From the close, the step reads consecutive windows as long as the plan's, with no overlap. It reads each only once it has ended and all its counted sources have read past it, and records the last one read in the package. Three consecutive watched windows, each with a share at least the baseline's, bring the case back, with at least five hit units among the three. An empty or lower-share window breaks the run. There is no pooled reference or shrinking test level. With the baseline as counted, among admitted and kept plans at 100 units a window, a removed problem returning to its old 10% share is caught within 26 windows about 74% of the time (74.1%), and within six about 37% (37.4%). A halved problem kept on a high baseline is caught about 60% (59.7%) and 25% (24.5%). False comebacks of a halved problem within 26 windows are 0.41%, 1.53%, 2.75% and 4.81% at old shares of 10%, 6%, 5% and 4%. A fixed-seed package test draws the baseline, gate and measurement before the watch, and pins these rates within the sampling tolerance of its kept plans. With an exact baseline at the old share instead, the exact false-comeback rates are 0.052%, 1.165%, 2.563% and 5.700%, respectively. At old shares of 3% and 2% they are 12.9% and 29.3%. Those exact-baseline rates also hold at 100 units a window; the count per window (old share times units) is what the rates depend on. These are finite-window rates, not a lifetime false-comeback bound. They assume independent units as well: a problem that clusters in sessions makes a window's hits vary more than they allow, and for it they are not bounds. A late run reads each ended window separately; a dry run saves no progress, even for a quiet window. A regression advances the case episode, so reports and failures from the previous episode cannot change it. A case that came back builds a new package, and the kept one's record stays beside it. Its lesson is published once; the back note says the lesson in tacit is not withdrawn.
- **The report** carries what the loop did, passively: a decided note when it lands a change (how to undo it), when it holds or makes a rollback, and when a problem it fixed is back; a shipped note with the measured effect when a change helped; a problem note while a change waits a window or more to be in effect, or its rollback keeps failing. None of them pages anyone. Each decision's note is written first, under an id of its own for the change (`shipped:CASE:COMMIT`, and `held`, `rolled-back` and `back-N` for the others, COMMIT the change's last landed commit), and only once: a note that cannot be written makes no decision, the run that comes back to the decision finds it written, and one the owner took out of the report is not written again. A rollback's note is put by the rollback's receipt, before the case leaves its measurement, whoever made the rollback. A landing uses the stable id `landed:CASE:COMMIT`. An unmeasured result has no result or zero due time in JSON. A stray measurement note or unreadable package fails only its own entry; the step logs it and continues with the other cases.
- **Prior art.** Fisher's exact test (Fisher, *The Design of Experiments*, 1935) is the exact test of two proportions. The conditional test of two Poisson rates ([Przyborowski and Wilenski, Biometrika 1940](https://doi.org/10.1093/biomet/31.3-4.313)) is its limit when the problem is a small share of its activity, and was this step's first test, until its activity held the problem's own events, which a change can move. Online experiments normalise a metric by its exposure because a raw count moves with traffic, and analyse it in the unit they randomise by, a user or a session, not the events inside it (Kohavi, Tang and Xu, *Trustworthy Online Controlled Experiments*, 2020): a session's hour is that unit here.

### Authority

- **Repositories.** The host maps repository names from the investigation through admitted `loop.read_dirs`. Origin's fetch and every push destination must name the same repository. Before every push, including proposals, landing, cleanup and rollback, the gate rechecks the source checkout and matches the host clone's destination to the package. The owner must be admitted by `loop.owners`, the repository absent from `loop.exclude`, the configured `loop.repo_guard` must allow it, and nothing else may be working there. A missing scope check refuses writes. Busy checks cover live sessions, processes, tracked changes and worktree activity in the last hour. Independent loop clones are outside the source's worktree registry.
- **Configuration and evaluation.** Configuration belongs to the owner and refuses unknown keys. The loop changes repositories through pull requests, never live configuration in place. Its own repository is default-deny for internal/, cmd/, sessions/, .github/ and every root file, including LICENSE, README.md, go.mod, go.sum, SPEC.md and AGENTS.md. This protects measurement and the session scanners that write the sessions events. Only internal/supervise/rules.go and internal/capacity/rules.go are allowed. Every other path in its own repository is refused, including a new top-level directory. Signal checks stop it from removing the problem it measures. In no repository does it change CI configuration (`.github/`, `.circleci/`, `.buildkite/`, `.gitlab-ci.yml`, `Jenkinsfile`, `azure-pipelines.yml`, `.travis.yml`): a pushed branch runs it, with the repository's secrets, before review. In its own it also leaves `internal/tracked/`, which CI builds from the tree. A test's scratch trees are removed through directory descriptors after restoring access to their directories, even beyond PATH_MAX. Cleanup never follows links. A tree that cannot be removed fails export, unexport or the sandbox step with that cause. A check or landing records no successful check or landing after a cleanup failure. Nothing bounds how much a test writes under `/work` and `/out` beyond the disk.
- **The relay.** Every model request uses the Bedrock relay. It admits only the global Claude profiles it has rates for (Opus 5.5 and Sonnet 5.5; the loop refuses to start with another model configured), bounds request turns and reserves the maximum charge before forwarding. Its limits are fixed: the dollars a run may spend through it are 1.5 times the run's budget, the requests it may make are 3 times its `MaxTurns` (the harness's `--max-turns` bounds the main thread only; subagents have turns of their own), at most eight are in flight, and a body is at most 8 MiB. A body is one JSON object with nothing after it and no key twice or in two cases, and `max_tokens`, read by that exact key, is an integer (or null) above zero and at most the model's output limit; the relay answers any other body 400 before it forwards anything, since it would price one value and the broker read another. The reservation of a request is its `max_tokens` at the output rate plus one input token for every byte of its body at the dearer of the input and one-hour cache-write rates, the true upper bound for text; a request whose reservation does not fit in what is left of the allowance is refused, so a run needs a budget of at least about 1.5 USD to start (the default is 4 USD) and a late request with a very large context can be refused where a smaller one would pass. An error answer of the broker (throttling, a malformed request, a model refusal), or a broker that does not answer at all (a refused connection), is billed nothing and is no turn; at most 40 of them are met before further requests are refused. The relay forwards the request's body and headers but not its query or cookies; the body's own fields that change a price are not inspected, so the rates above are the relay's estimate and the reservation its bound. Usage by token kind and cost come from responses the relay observed. Harness claims are diagnostics. A terminal report must match the terminal structured output the relay observed. Refusal, fallback allowance and accounting use those observations.
- **Run directories.** A run's directories (`runs/ID` for what it wrote, `runs/.ID-host` for the host's archive, up to 64 MiB of transcript) have no retention yet, and nothing bounds the size of what a run writes, or what a check writes into its export, under `/work` and `/out` beyond the unit's memory and the disk. A broker that is unreachable fails a run as `broker`, which the stop rule does not count.
- **Budgets.** Defaults remain $4 per run, 30 minutes and 120 turns; $20 per case, $40 per day and $200 per week. Reservations precede runs and count at their whole budget. A fallback shares the remaining spend, turns and time. A fallback that never starts adds no charge. A run with no observed request holds its reservation; unknown usage holds its request reservation. Cancellation stops the whole unit. `Result.Failed` is diagnostic only. Host lessons use no model reservation.
- **The stop rule.** Two completed live runs of the same step with the same failure stop the case. Refused, running, never-started and experiment-tagged runs do not count, and neither do the runs the host ended (`stopped` by a signal, `killed` by a restart) or the ones the broker never answered (`broker`), or a review held at its recording (`hold`): they say nothing of the agent. Only the current case episode counts. The loop files a component-health case with both archived transcripts and moves on. Preparation, patch, check and proposal failures have stable separate keys.
- **Trust and scrubbing.** Everything a run writes is untrusted data. The host takes report text and one confined diff, applies it in its own clone and runs checks itself. It never runs programs or Git on the host in a run directory. The separate sandboxed patch unit owns Git there. Partial investigations have the one confined findings read. Trusted inputs, archives and journals stay outside writable mounts. Generated text is cleaned whole before clipping, persistence or display; cleaner failure withholds it. Deployment and rollback clean their log text before opening the store transaction. Patch, tree and package text given to a reviewer are data, never instructions. Public also replaces home paths, e-mail addresses, IP addresses and domain-shaped host names. An IPv6 token must parse as an address and contain at least two groups. A non-hex label before its first colon, such as ip: in ip:2001:db8::1, is kept while the address is masked. Two compressed lowercase hex-letter identifiers such as a::b stay code; digits, uppercase hex letters or at least three groups establish address context. Identifier paths, namespace syntax and slices stay code. A host name needs a suffix from the short list and address context: a URL, an @, a host: or ssh word, a path after it, or a lowercase hostname-like token with at least three labels. Short identifier-like receivers, named receiver paths, uppercase identifiers, names inside a dot-chained expression and calls stay code without explicit address context. A bare two-label domain, such as example.com, is not caught. Source file names such as main.go, notes.txt and config.json, versions such as go1.22.3, and dotted identifiers such as cfg.app and self.name stay intact. The host reads repository visibility before posting or creating or editing a pull request. Unknown visibility refuses the post. A repository that is not private receives only host-built ids, counts, a diff stat, check exits and base and head commits. Its commit message is host-built too. Before the first proposal push, and on every later proposal or landing push, the host scans the cumulative patch's added lines and added file names with the same personal-content masks and secret scrubber. Binary-classified additions are scanned as text. A hit refuses the push with its cause; code is never rewritten by a scrubber. A private repository is unaffected. Builder and reviewer prose stays local. The case mechanism is never added to a proposal body. Both run skills exclude real-store text, paths and names from title, body and findings. Failure keys stay separate. Repeated refusal notes are compared in their cleaned, single-line, clipped storage form. Ending, charging and logging a run is one transaction, applied once.
- **The owner's attention.** No run reaches the owner's phone or desktop. Posted mentions and references are inert. Cases, runs and passive report notes carry the results; nothing wakes or pages anyone.

Prior art: Claude Code's [print mode](https://code.claude.com/docs/en/headless) supplies native agents, schema output and turn and spend caps. The loop adds host reservations, a stop rule, a whole-process sandbox and a relay that keeps credentials outside it. The maintained sandbox's prior art is listed in Sandbox.

## Evaluation

The golden evaluation compares the loop's investigation with the harness's native agent on the same tasks. A task is a past problem with a verified root cause and fix. The loop arm receives a symptom case's live investigation prompt and records its findings in that case. The native arm receives the native brief and the symptom event ids. Both use the same Agent path, system prompt, report schema, models, relay, limits and sandbox as a live investigation. Neither system prompt loads today's rules files, which can hold later lessons. Both keep the owner's standing constraints. Fixtures in this repository are synthetic. The golden file and its answers stay on the machine.

Before a golden run, the operator freezes the procedure, holds out tasks from writing it, and checks the judge against a sample graded by hand. The command records the held-out ids, selected split and selected task ids. It does not certify that the operator kept the split or checked the judge. `--held-out ID,...` records the split. `--split all|development|held-out` selects it; a selected split needs held-out ids. `--task ID,...` narrows that selection. The split is explicit, not a random split changed by each run.

`momentum loop eval --golden FILE --task ID,... --trials K --arms loop,native --budget USD --parallel N` runs the experiment. The default golden file is `~/.local/share/momentum/golden/golden.jsonl`. The defaults are three trials, both arms, $120 and three pairs at once. A single arm can run alone. Every JSONL line has these exact keys:

| Key | Meaning |
|---|---|
| `id` | Unique lowercase slug. |
| `family` | One of the store's case families. |
| `case_title` | The symptom title. |
| `symptom` | An object with `query`, itself an object with `event_ids`, a nonempty array, and optional `text`, the owner's note on the symptom, which no trial sees. |
| `cutoff` | A nonzero RFC3339 time. |
| `root_cause` | The verified cause, given only to the judge. |
| `key_facts` | A nonempty array of verified facts, given only to the judge. |
| `wrong_paths` | Optional wrong diagnoses, given only to the judge. |
| `repo_path` | Optional local repository path. |
| `repo` | Optional repository label; it requires `repo_path`. |
| `pre_fix_commit` | Optional provenance. It does not select a checkout or enter an investigation. |
| `title` | Optional descriptive metadata. It does not enter an investigation. |
| `harness` | Optional label of the harness the cause involves. It does not enter an investigation. |
| `difficulty`, `fix`, `verification`, `evidence`, `reach`, `reach_detail` | Optional notes the owner keeps beside a task. They are dropped before the task is read: the evaluator keeps none and no trial sees them. |

Unknown, differently cased and repeated keys are refused, including nested symptom keys. The command reads the bytes once, parses them with `DisallowUnknownFields`, and hashes those same bytes. Blank lines are ignored. Duplicate ids and unknown selected ids are errors before setup.

**The end.** A task's end is the earlier of its cutoff and one minute after its newest symptom event. Missing or undated symptoms fail preparation. The store contains events in the 30-day window ending there, inclusive at the start and exclusive at the end, and notes in that window. `StoreCopy` scrubs every text column and removes every case, run, package and derived table. Mutable `incidents` incident rows and `radar` findings are omitted. Incident sightings remain. The task's case opens from its symptom title and events alone.

**Shared inputs.** The host prepares the inputs once per task, before its first arm starts. Both arms and every trial of that task mount the same files read-only at `/ro/store.sqlite`, `/ro/records`, `/ro/config`, `/ro/repos/NAME` and, when available, `/ro/clone`. Records are collected by `Records` from the scrubbed snapshot, using a pinned copy of the evaluating momentum binary as a host child. That child gets `MOMENTUM_NOW` set to the task's end. Raw evidence, neighbours, unit logs and their unavailable states are frozen before any arm starts. The normal records limits apply. Each trial records the complete records manifest, its stopped bound and hashes of every published file, including each unit output. A task whose records capture reached a bound is left out of the paired comparison. Inputs are removed after that task's last trial, including its judges. No arm clones them again. The host's per-arm case store is private and removed when the arm ends.

**Historical repositories.** Every task receives every repository named by the golden file, independent of selection, numbered consecutively from `repo-1`. A repository with no commit before the end is omitted, and so is one the scrubber would change (an object it would mask, or over 8 MiB); it is listed in the task's manifest as refused, without its name, and both arms see the same set. Tacit's clone is left out the same way. Its local default branch sets the historical head: `origin/HEAD` names that local branch, with local `main` or `master` as fallback. A fetched but unpulled remote head does not select it. When its reflog covers the end and a current branch or tag still reaches that historical commit, the reflog selects the branch's position. Both the reflog and date rules use the last whole second strictly before the end. Otherwise commit dates approximate the position. An independent `--no-local` clone checks out that commit. Later refs, tags, reflogs and unreachable objects are removed. Alternates and remaining unreachable objects are refused. Escaping or unresolvable work-tree links are removed without following them; their historical blobs remain. Hooks and origin are removed. Git uses the host input execution pins and clean environment. The published objects and metadata must pass the same scrubber as live inputs.

**Tacit and configuration.** Tacit's store is a Git clone selected and pruned by that same historical rule. It is mounted at `/ro/clone` only if it held a commit before the end. Its files are searched directly. No tacit executable, index or warm-up runs. `ConfigCopy` receives `AsOf` set to the end. Tracked configuration comes from its historical commit strictly before the end. Roots outside a repository are copied as they are now. Each task records those roots in `inputs.configuration.leaks` in `results.json`.

**Known limitations.** Historical Hermes message rows are withheld in full whenever `MOMENTUM_NOW` is set. Hermes rewrites old rows in place, and the earlier bytes cannot be certified. Their stored event summaries remain. Ingest reads Hermes through the normal reader, with no full-database digest snapshot. An ordinary referenced record dated at or after the end is withheld. An undated record at a sessions or supervision scan's place is withheld too. A mistakes record must still match its stored line hash. Unit records use only the journal strictly before the end, never today's service state. An event summary reflects its last ingestion, which may have re-derived an older event. Rebuilt incident sightings cannot reconstruct their original text. Unavailable or pruned transcripts cannot be recovered. Git dates are an approximation when the source reflog does not establish the earlier position. These limitations are listed in `results.json`.

**The trial.** Both arms have the same pinned `momentum-ro` at `/opt/momentum/momentum-ro`, on PATH, reading the same task copies. It changes nothing. No tacit program is mounted. An investigation also reads files with the harness's tools. Both prompts start with the live investigation question and end with the same paths reference for `/ro`: the evaluation's, which describes its as-of clones with their history (a live run's describes snapshots, and the evaluation does not use them). The loop prompt lists the case's newest 20 pieces of evidence. The native prompt names every symptom event id. The shared snapshot and records still hold all available symptom events. Both keep Mechanism, Alternatives ruled out, Fix and Summary in `/out/findings.md` as they go, and end with the live investigation schema report. The host reads both arms' findings the same way. The loop records its mechanism, alternatives and fix in its private case, in the reserved episode, as live. A cut-short run is graded from those retained findings. A findings file's summary is omitted from both arms because the case has no summary. Every published prompt and system prompt passes the scrubber.

**Isolation and names.** One evaluation runs at a time on the user's service manager: a second, from any data home, fails at once on the lock of its unit prefix (`momentum-run-eval.lock` in `$XDG_RUNTIME_DIR`, else in the user's cache directory under `momentum`). The lock guards the sweep below, which stops every unit of the prefix whatever home started it; a test process's own prefix has a lock of its own. Before an evaluation, `sandbox.Available(true)` probes the real launcher and `sandbox.StopLeftover(ctx, "momentum-run-eval-")` stops only leftover evaluation units. Each trial, fallback and judge has a unique unit beginning `momentum-run-eval-`. Task ids, answers, the golden file, live stores, source files and other trials' directories are never mounted in an investigation. Opaque hashes name trial directories and experiment tags; a repeated directory is refused without clearing it. The sandbox holds only the trusted input directory, shared `/ro` inputs, harness binary, pinned read-only momentum binary, empty `/work`, writable `/out` and its private relay. The same fixed startup witness as a live investigation distinguishes entry into the sandbox from merely starting its launcher. A failed start has no start time, costs zero and leaves its pair out of the comparison. It remains an error with its reason, not a budget skip.

**The judge.** A clean-context judge has no tools, fallback or investigation inputs. In addition to the fixed sandbox layout and its harness and relay, only its input directory is bound. It has no `/ro`, `/work` or `/out` mount. A random opaque directory names it. Its prompt holds the verified cause, key facts, wrong paths and four equally folded and capped findings fields in a fenced block. Each field is capped at 2,000 bytes. Fences in the text are JSON-escaped. The loop contributes its case's mechanism, alternatives and next test plus the report summary. The native arm contributes the same fields from its report or running findings. No root signature, task id or arm name goes to the judge. The grade schema requires exact `verdict`, `facts` and `reason` members, their types and no extras. Each fact requires exact `fact` and `reached` members. Repeated or differently cased members are refused. Verdicts are reached, partial, missed or wrong. A failed or malformed judge is retried once on the same model. Both archives and both costs remain. Two failures retain the actual schema or run error and leave the pair ungraded.

**The store.** The evaluation scrubs the store once, for the widest window its tasks need (from the earliest end less 30 days to the latest end), and cuts each task's copy from that master by time (events from the window, notes before the end, `done` times at or after it cleared, in-place incident and radar rows left out as before); the master is removed when the evaluation ends and no run can reach it. A task whose end cannot be found is left out of the master's window and fails alone.

**Scheduling and budget.** Jobs are interleaved by trial and task. Each slot runs both arms and their judges together. The arms take turns going first, alternating with the trial number and task position: half the pairs, within one for an odd count, whatever order `--arms` names them. A mutex reserves all arms before either starts. Each arm reserves 1.5 times its investigation budget plus two judge budgets, including the relay's allowance for each. With the default $4 investigation and $3 judge this is $15 per arm and $30 per pair; a judge needs that room because the relay reserves the largest charge a request could cost, and its request carries both investigations. The `--budget` cap must therefore hold $30 for every parallel slot plus what was spent: a pair is skipped when it does not. Each arm releases its reservation when it settles. A budget stop skips both together. Accounting uses only `Result.USD`, `Result.Usage`, turns and time observed by the relay and host. Harness-stream prices and tokens are diagnostics. A started run with no observed request holds its named reservation. Unknown response usage holds the relay's request reservation. Investigations and judges carry experiment tags and do not count toward live budgets, stale recovery or the stop rule. Both reservation and completion store errors are reported. Never-started rows are listed by their end time and do not add to a case's run count.

**Results.** The summary keeps all started investigations' cost, time, relay tokens and errors. A pair enters comparison only when both arms started, neither has a bounded capture, and both judges produced valid grades. Ungraded, excluded and budget-skipped trials are visible separately. Pass@k is the fraction of compared tasks with at least one reached trial; pass^k requires all requested k. A missing trial cannot pass^k. A flip is disagreement on reached among graded trials. Per-cause cost and time use only compared trials and divide by their reached causes. Undefined rates serialize as null and print as undefined. Distinct error texts print beside each arm's counts. Per task the summary names which arm reached more often. A paired bootstrap resamples tasks with all their trials together, uses seed 1 and 10,000 draws, and reports nearest-rank 5th and 95th percentiles for loop minus native reach per dollar and per minute. A zero denominator in any draw makes that interval undefined. Few-task percentile intervals can cover less than their nominal 90%; the task count stays beside them. The loop goes live only when it reaches verified causes at less cost and time per reached cause than the native arm.

**Provenance.** `results.json` records the evaluating build's revision and dirty state from `debug.ReadBuildInfo`, or unknown when unavailable; the exact golden bytes' hash; every investigation and judge prompt hash; the system prompt hashes; the pinned host momentum binary's SHA-256; budgets; requested and observed models; task selection and held-out split; input manifests and hashes; all trial records; summaries; intervals; and known limitations. The evaluating binary is copied once, never linked, so an install or rebuild during a run cannot change the records child. The same pinned binary is mounted read-only as `momentum-ro` in both investigation arms, never the judge. Its hash is also recorded as `momentum-ro` in `program_hashes`, and its fixed bind destination and hash are in the input manifest and published input hashes. Empty evaluations still write results. A failed results write fails the command.

**Prior art.** [SWE-bench](https://www.swebench.com/SWE-bench/guides/evaluation/) evaluates against a task's base checkout. These trials also remove later refs, reflogs and objects. [Chen et al. 2021](https://arxiv.org/abs/2107.03374) describe pass@k; [tau-bench](https://arxiv.org/abs/2406.12045) uses pass^k. [Zheng et al. 2023](https://arxiv.org/abs/2306.05685) describe position, verbosity and self-preference biases in model judges. Equal fields and caps reduce arm cues. Repeated trials and hand grading check what a single verdict cannot establish.

Scorecard:
- owner interventions and corrections per week;
- recurrence of root causes after their fix;
- improvements shipped with a measured benefit;
- pages and questions to the owner;
- false alarms;
- model spend.

Fewer questions does not count as success when it comes from unauthorized assumptions.
